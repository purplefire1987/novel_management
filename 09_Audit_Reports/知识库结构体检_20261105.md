## 三、逐项说明

### 1. 分层与目录职责 — 9/10

`00_System` 到 `12_Dashboard` 是「引擎 → 事实 → 记忆 → 大纲 → 素材 → 伏笔 → 图谱 → 正文 → 审计 → 变更 → 模板 → 看板」的单向流，编号本身就是阅读顺序。
`99_Archive` 收尾，与 `00_System` 形成首尾双保险。

扣 1 分：`02_Hot_Memory`（当前状态）与 `03_Short_Term_Memory`（滚动摘要）职责重叠，目前前者 2 页、后者 3 页，实际只有 `Current_Story_State` / `Current_Volume` 在真正运转。

### 2. 单一事实源 — 8/10

- `01_Core_Memory` 内 596 个实体 ID **无重复**（`CH-0001/0002` 各两处是大纲 + 正文，属设计）。
- 同名档案只保留一份，旧稿统一降级到 `99_Archive/Original_Draft` 并标 `deprecated`。

扣 2 分：这条纪律**靠代码自觉维持，没有硬守卫**。本轮就抓到三类"影子事实源"：

1. 177 个 `.tmp_*` 半成品散在 `Characters/`、`Locations/`，每个都带完整 frontmatter 和同一个 `id`——
   而 `pathlib.Path.glob("*.md")` **会**匹配点开头文件（与 `glob` 模块行为不同），
   于是这些残骸被当成真档案读进来，实体数一度虚高到 627。
2. 12 个无 `LOC-` 前缀的州域档案（`0078_湖州.md`），来自生成脚本的 ID 截断 bug。
3. Vault 内曾存在隐藏回收站 `.trash_20261104/`，示例档案 `CHAR-0001_沈砚` 抢占真档案位。

### 3. 双链完整度 — 9/10

4366 条 `[[...]]`，**0 断链**。地图页 72 个城邑全部双链到档案，州 › 府 › 城 三级互相可达。

修掉的问题：三张底层设定页的编号整体错位一格——
`WORLD-0002_三质` 实际是 `WORLD-0001`，`WORLD-0003_三重循环` 实际是 `WORLD-0002`，`WORLD-0004_第一因` 实际是 `WORLD-0003`，
5 个页面据此引用了不存在的目标，共 10 条链接。已按「以 `id` 字段为准」统一校正。

扣 1 分：40 页无入链。其中 `99_Archive` 原件的孤立是合理的（存档本就该被封存），
但 `03_Short_Term_Memory/Active_Context.md`、`Rolling_Summary.md` 两页既无入链也无内容，属空转。

### 4. 索引可达性 — 9/10

两条通道互补：

- **人读**：`07_Entity_Graph/Entity_Index.md`（944 行，按类型分组、按 ID 排序、表格内竖线已转义）。
- **机读**：`.novel_system/index.sqlite` + `novel find / search / show`，名称 > 别名 > 概要三级排序。

扣 1 分：索引只在跑 `novel rebuild-index` / `novel publish` 时刷新，Obsidian 里不会自动更新；
索引页首也不写 `generated_at`，无法一眼判断新鲜度（当初是为了避免每次重建产生无意义 diff，属有意取舍，但代价是可观测性）。

### 5. 命名与编号 — 9/10

- 档案一律 `ID_名称.md`，`01_Core_Memory` 内 748 页合规率 100%。
- 双号段：`CH-0xxx` 给新版主序列，`CH-1xxx` 留给旧稿存档，`ids.py` 里有 `reserved_bands` 硬拦，
  否则新章会被推到 `CH-1029`（这个坑已经踩过一次，`test_ingest` 8 项因此挂掉）。
- 别名进 `aliases`，正文与检索都能命中（如 `武安都` 别名 `江陵郡`）。

扣 1 分：本轮清出的 12 个无前缀档案说明**生成脚本没有写后自检**——如果当时校验"文件名必须匹配 `^[A-Z]+-\d{4}_`"，这批脏数据根本生不出来。

### 6. 归档与卫生 — 7/10

三处分层是清楚的：`99_Archive/Raw_Sources`（原件）→ `99_Archive/Original_Draft`（旧稿正文）→ `10_Change_Log`（变更与回滚记录）。

但要扣 3 分，因为本轮清理出的残骸量级失衡：

| 清出物 | 数量 | 成因 |
| --- | --- | --- |
| `.tmp_*` 写入半成品 | 177 个 | 沙箱拒绝 rename → 每次写盘留一个临时文件 |
| 测试残留 | 39,831 个文件 / 266 MB | `pytest` 的 basetemp 落在 Vault 内，从未清理 |
| 无主州域档案 | 12 个 | 生成脚本 ID 截断 |
| 仓库根 8 字符垃圾文件 | 7 个 | 上一次安全守卫死锁时的残留 |

清理后仓库从 320 MB 降到 54 MB。

### 7. 可维护性 — 8/10

命令面完整：`doctor / preflight / write / review / publish / commit-memory / audit / rollback / ingest / import-assets / import-lore / dice`，
外加四个生成脚本（`build_jiuzhou_map` / `import_map_admin` / `link_entities_to_map` / `split_original_draft`），全部幂等可重跑。

扣 2 分：
- 生成脚本普遍缺「写后校验 + 幂等测试」，`build_jiuzhou_map.py` 就因 `group(1)` 取错而重复建过州档案、错建过 12 个无前缀页。
- 实体 ↔ 地图联动此前是**一次性**的（`import-assets` 写完就断），现已改成可重算投影，挂在 `rebuild-index` 与 `publish` 两个触点上，跑两次结果一致（第二次 `files_touched = 0`）。

## 五、给结论

这套库的**骨架是合格的**：分层清楚、事实源唯一、链接零断、索引双通道、流程带门禁（preflight 不过不许写）。
它现在最大的风险不在结构，在**派生层的覆盖率和脚本的自律**——
地图能覆盖 85% 的势力和 37% 的人物，但物品与生物是 0；生成脚本能跑，但跑完不检查自己写了什么。

前者靠补数据，后者靠加断言。两件事都不难，但都要一次一次地做。
