# ADR-006：Agent 默认写 staging，作者最终批准

- **状态**：已接受
- **批准人**：作者
- **日期**：2026-11-20
- **相关**：ADR-002、ADR-007

## 背景

九个 Agent（总编、世界架构师、编辑、骰子娘、资料官、主笔、记忆管理员、录入员、版本管理员）
都会产出内容。其中一部分会直接改变 Canon 或正文。

旧系统的做法是「路径白名单」：给每个 Agent 一份可写目录清单，靠 `startswith` 判定。
这套机制在目录拍平（`06_Manuscripts/02_草稿/` → `06_Manuscripts/`）后失效了，
主笔对自己唯一的写入范围变成越权——白名单没跟着改，而代码不会报错，只会拒绝。

## 问题

「谁能写哪里」如果只写在一张静态清单里，清单就会与目录结构脱钩。
更根本的问题是：**Agent 不该有直接写正式区的权限**，无论它的白名单怎么写。

## 决策

**物理上分两段：Agent 只能写 staging，正式区只能由 CLI 在作者批准后写入。**

```
Agent 产出  →  07_Staging/<TASK-ID>/<分栏>/...
作者审阅    →  novel diff（只读）
作者批准    →  <runtime>/approvals/APR-*.json（绑每个文件的 sha256）
写入正式区  →  novel publish（四道闸）
```

四道闸依次是：

1. 存在有效批准记录；
2. 每个文件当前 sha256 与批准时一致（批的是 A、发的是 B 在此不成立）；
3. 没有批准范围之外的新增文件；
4. 目标合法——写 `01_Canon/` 另需 `--confirm-canon`。

`approve` / `publish` / `adopt` / `restore` 只接受 `--as author`；Agent 代办返回退出码 3。
Agent 权限矩阵（`agents/common/permissions.md`）里，Canon 写入一列九人全是 `X`。

## 备选方案

| 方案 | 为什么没选 |
|---|---|
| 路径白名单 + `startswith` | 已失效：目录改名后白名单不变，且不报错 |
| Agent 直接写 Canon，靠事后审计 | 审计是事后诸葛亮，改坏了要回滚，而回滚不一定有备份 |
| 只靠 Prompt 约束「不要写 Canon」 | Prompt 是软约束；模型换版本、上下文变长都会漂移 |
| 用文件系统权限（chmod / ACL） | 跨平台行为不一致，且 Obsidian 里作者要能改，权限会很别扭 |

## 影响

- 每次内容入库多两步（`stage`、`approve`），但换来「批的确实是发的」；
- 批准会被内容变化自动作废，不需要人工记得撤销；
- 代价：Agent 无法「顺手改一下」正式文件，必须走完整链路——这是设计意图。

## 验收方式

`tests/integration/test_workflow_flow.py` 覆盖：非作者批准被拒、未批准发布被拒、
批准后篡改 staging 被拒、Canon 缺二次确认被拒、重复发布被拒。
