# ADR-016：原稿导入以「原始字节 + 行号定位」为准，分维度记账，分批进 staging

- 状态：已接受（2026-11-21）
- 关联：细化 ADR-006（staging 后由作者批准）、ADR-014（批准绑定字节）；
  依赖 ADR-015（发布按 22 步切换）；PRD §12.1–§12.4 与 T07 验收
- 取代：无

## 背景

旧稿导入要回答四个问题，四个都容易答错：

1. **原文会不会被改坏**。别人的稿子可能是 GBK、可能带 BOM、可能一份里混了多个文件的结构。
   任何一次「顺手转码」「顺手整理段落」都可能悄悄少几个字。
2. **发布候选能不能指回原文**。一句正文是从哪来的？答不上来，后续校对与法务都无从谈起。
3. **一次导入到底成了多少**。「导入成功」这四个字能盖住「三份收了两份」「五章切出四章」
   「九段丢了一段」。
4. **原稿不是正式内容**。它得先进提案区，由作者决定哪一章进正文。

## 决策

### 1. 原始字节单独保全，且写后回读校验

被接收的文件原样复制到归档区 `Imports/<IMP>/raw/`，**逐份回读 sha256 比对**，
不符即中止整次导入。不做转码、不做换行归一化：GBK 文件直接拒绝并说明
「本系统不猜编码」，让作者自己转成 UTF-8。

理由：转码是不可逆的猜测。猜错了不会报错，只会让原文少几个字，
而系统此后所有「来源引用」都指向这份已经坏掉的底稿。

### 2. 定位符只用文件名与行号

格式 `<文件名>#L<起>-L<止>`，单行时 `#L<行>`。三项都不带：

- **不带章号**：章号是解析结果，换一次切分规则就全变；行号是原稿坐标，不会变。
- **不带块 ID**：块 ID 由解析器生成，属于派生数据，重建即改。
- **不带字符偏移**：偏移在换行符归一化后会整体平移，不如行号稳。

定位符必须能反查回原文（`import where`）。抽样核对的就是这件事。

### 3. 十一个维度各自记账，没有 `success` 字段

`ImportManifest` 逐维度落字段：接收/拒绝、原始字节保全、解析异常、段落归属、
来源可解析、提取覆盖、抽样准确率、阻断冲突……每个维度自己给结论，
`verdicts()` 逐条列出，`blocking()` 只列**会让发布候选不成立**的那几条。

Schema 里 `additionalProperties: false`，顺手加个 `ok: true` 会被校验拒绝。
**「总之成功了」是这份清单最不该有的一句话**：它一旦存在，所有维度就都白记了。

两条口径要分开：

- 未映射段落**不阻断**（PRD §12.4 允许「映射到解析结果**或**显式未映射区」），
  但它让「段落全部有归属」这一维度不达标；
- 提取覆盖不完整**不阻断**（不能让「这章没提到人名」变成「这章不许进正文」），
  但它让「提取覆盖完整」这一维度不达标。

### 4. 抽样只量定位准确率，不冒充语义准确率

`accuracy` 的定义写死在 `note` 里：**抽样条目的定位符能否反查回原文**。
「这段话里是不是真有个叫某某的人物」需要人看，系统不代劳。
0 条样本时 accuracy 记 `0.0` 并说明「不适用」——没有样本的通过率不是通过率。

### 5. 进 staging，不进正式区；分批发布走既有 22 步

`import scan` 只写归档区（原始字节）与 runtime（报告）；`import stage` 只写 staging。
发布仍是 T06 的 22 步，作者在中间批准。导入**不是**一条绕过审批的捷径。

### 6. 台账覆盖整个导入计划，不是「这一批」

台账落在同一个目标文件 `05_Ledgers/Imports/<IMP>.md` 上。若每批只写自己那一批，
第二批发布时会把第一批的章整段抹掉——报告于是「看着完整」，实际只描述了最后一次操作。

所以台账按**全计划**渲染：已发号的写 CH 号与目标文件，未发号的写「尚未发号」，
空章写「不进正文」。各批已发的号持久化在 `<runtime>/imports/<IMP>/assignments.json`，
重跑同一批复用原号，不再吃新号。

### 7. ID 查重分级，staging 不算撞号

`IdRegistry` 扫全 Vault，但**判重按区域分级**：

| 情形 | 判定 |
|---|---|
| 正式区内同一 ID ≥2 份 | 真撞号，发号必须停 |
| 正式区 1 份 + staging/审阅 1 份 | 同一对象在途，不算撞号 |
| 正式区 1 份 + 归档 1 份 | 告警，不拦截 |

不分级的后果是**发布过一次就再也发不出号**：第一批发布后正式区与 staging
各有一份 `CH-0001`，旧实现判成重号，第二批直接卡死。T07 冒烟时撞上了。

区划由 `ProjectPaths.area_roots()` 提供，目录名不写死。**不传区划时全库按正式区处理**
——宁可从严，也不能因为调用方忘了传参就悄悄放松查重。

### 8. 计划里的路径是项目相对，清单与快照是 Vault 相对

这是 T06 留下的一处坐标系混用，T07 一并修掉：`apply_changes` 直接把
`03_Manuscripts/...` 落到快照根，制造出「Vault 里不存在、索引里却有」的幽灵文件，
搜索会命中一个打不开的路径。

现在两个方向各有一个函数（`vault_rel` / `project_rel`），**互相拒绝对方的输入**，
把「混用不报错」变成「混用立刻报错」。

## 备选方案

- **一次导入全量进 staging，不分批**。选批是因为旧稿动辄上百章，
  一次批一百章等于让作者没法逐章看。分批后每批都是一个可独立审阅、独立发布的单元。
- **原始字节放 runtime**。选了归档区：原文不可重建，属于作品资产；
  runtime 是「可删可重建」的地方，把原文放那儿等于给它贴上可删标签。
- **用块 ID 做定位符**。块 ID 短、好查，但它是解析产物。解析器改一次（比如
  调整段落合并规则），全库历史定位符就同时失效——比现在多一层不可控。
- **自动识别 GBK/GB18030**。选拒绝：识别靠猜，猜错的代价是静默改字。
  「请先转成 UTF-8 再导入」是一句能照做的话。
- **导入时顺手把候选提及写成实体档案**。那是替作者做设定决定。
  候选一律 `approved: false` 进台账，作者点头才谈事实（ADR-014 的同一原则）。
- **台账按批分文件**（`IMP-000001-B1.md`）。会引入不合 §8.1 的复合 ID，
  或者干脆没有 ID 的孤儿文件。整份覆盖渲染更省事，也不丢信息。
- **发号时一律 `--allow-dirty`**。那等于关掉查重。分级查重是「知道自己在放过什么」，
  `allow_dirty` 是「闭眼发」。
- **让 `publish` 直接从原稿读字节**。绕开 staging 就绕开了批准。

## 影响

- 新增 `src/novel_management/importing/`（model / scanner / preserve / parser / extract /
  sampling / report）与 `cli/import_cmd.py`；命令行 27 → **28 条**（新增 `import`，
  含 `scan`/`report`/`stage`/`where`/`list` 五个子命令）。
- `schemas/import_manifest.schema.json` 的 `files.items` 补上
  `format`/`encoding`/`lines`/`rejected` 四个字段——原来的字段集连自己写出的清单都过不了。
- `ids.py` 的 `IdRecord` 增加 `area`，`IdRegistry` 增加 `conflicts()`/`tainted()`/
  `pending_copies()`；`IdAllocator` 增加 `areas` 参数。
- `release/workspace.py` 增加 `vault_rel`/`project_rel`，`apply_changes`、
  `build_snapshot`、`_check_file_set`、`release_change_loader` 一并改签名。
- 原始字节进 `90_Archive/Imports/<IMP>/raw/`（**归档区，不发布**）；
  报告与已发号记录进 `<runtime>/imports/<IMP>/`。
- 已知限制：docx/epub/pdf 属 P1，本版明确拒绝；人名类候选需要先有实体档案
  （词典来自 Canon 的 `name`/`aliases`），纯描写章必然落进「待提取」。
