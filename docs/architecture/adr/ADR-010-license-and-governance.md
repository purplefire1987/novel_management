# ADR-010：公共仓库的许可证与贡献治理

- **状态**：已接受（2026-11-20 作者拍板：GPL-3.0-only）
- **批准人**：作者
- **日期**：2026-11-20
- **相关**：ADR-001、ADR-005

## 背景

这个仓库既是作者自用系统的代码，也是一个可能被他人复用的工具。
但它的使用者天然分两类：写作者（关心作品归属）与开发者（关心代码许可）。

## 问题

- 若使用宽松许可（MIT/Apache），他人可自由复用代码，包括拿去搭商业写作服务；
- 若使用严格许可（AGPL），作者自己用没问题，但会挡住一部分想复用的人；
- 若暂时不定，仓库处于「谁也不能合法复用」的状态，但代码本身仍然公开可读。

## 决策

**采用 GNU General Public License v3.0（`GPL-3.0-only`）。**

- `LICENSE` 放 GPL-3.0 全文（取自 gnu.org 官方 `gpl-3.0.txt`，674 行）；
- `pyproject.toml` 的 `license` 写 `GPL-3.0-only`，classifier 同步；
- 贡献者提交即表示同意其贡献以 GPL-3.0 发布；
- 代码许可与**作品内容**的归属彻底分开：作品内容从不进入本仓库，
  所以「代码用什么证」不影响「小说归谁」。

为什么是 GPL-3.0 而不是更宽松的证：

- 这个系统会被拿去搭写作服务是现实可能，而作者不希望自己写的工具
  变成别人闭源产品的底座；
- GPL-3.0 不阻止商用，只要求**分发衍生作品时同样开源**——自己用、改、卖服务都不受限；
- 相比 AGPL，GPL-3.0 不把「通过网络提供服务」也算作分发，对想本地部署的人负担更小；
- 相比 MIT/Apache，它保住了「改了什么要让人看见」这一条。

未采纳的方案：

| 候选 | 未采纳的理由 |
|---|---|
| MIT | 允许闭源衍生，与「不想被拿去搭闭源服务」的意图相反 |
| Apache-2.0 | 同上；专利条款对本项目不是主要诉求 |
| AGPL-3.0 | 把 SaaS 也纳入分发，对只想本地跑的用户过重 |
| 专有（保留所有权利） | 仓库公开却不可复用，等于既不分享也不保护，最差的一种 |
| 继续 `LICENSE_PENDING` | 「谁也不能合法复用」同样阻止了正常使用，只是把问题往后推 |

## 贡献治理

- 单维护者模式：作者是唯一有权合并的人；
- 外部贡献走 PR，必须过 CI 三项（测试、隐私扫描、边界守卫）；
- 涉及 ADR 所列决策的改动，先讨论 ADR，再改代码；
- 不接受含真实作品内容的贡献，无论是否脱敏。

## 影响

- 代码可被自由使用、修改、商用；分发衍生作品时必须以 GPL-3.0 开源；
- 若日后换证：需征得全部贡献者同意（目前只有作者本人），改 `LICENSE`、`pyproject.toml` 与 README 的一节；
- 风险：GPL-3.0 与部分闭源生态不兼容，想把它嵌进闭源产品的人会因此放弃——这是有意为之。

## 备注

这篇 ADR 曾在 2026-11-20 上午以「许可证待定」结案。同日晚作者给出明确选择，
故改为已定，并把当时列出的候选与理由保留下来——**记录为什么没选别的，
比只记「选了哪个」更有用**，下次有人问「为什么不是 MIT」时不用重推一遍。
