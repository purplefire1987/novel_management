# ADR-018：草稿只能在 staging、审核不许自审、正文与记忆同批

- 状态：已接受（2026-11-21）
- 关联：细化 ADR-006（Agent 默认写 staging）、ADR-014（批准绑定字节）；
  依赖 ADR-016（原稿导入的分维度记账）、ADR-017（Preflight 与角色权限）；
  PRD §10、§14、§15 与 T09／T10 验收
- 取代：无

## 背景

T09 与 T10 要做的是「从规划到正文，再到记忆」的闭环。它比前面的任务更容易做歪，
因为每一步都有一个「看起来完成了」的实现，代价要到很晚才显现：

1. **草稿写哪**。写进 `03_Manuscripts/` 与写进 `01_Canon/` 都能跑通，
   而且后者看起来更「方便」——反正要发布的。但一旦草稿进 Canon，
   「未批准内容不得进入正式事实源」这条就只靠人记得。
2. **谁来审**。让写稿的角色顺手打个「通过」最省事。可这也意味着
   风险路由、专项角色、总编汇总全部可以省略。
3. **返修几轮**.不设上限，稿子会一直改下去；设了上限却只在界面上提示，
   程序照样接受第 N+1 次审核，预算就等于装饰。
4. **记忆什么时候提取**。要求正文先发布再提取，最好实现，但必然出现
   「正文已生效、记忆还是上一版」的窗口：`state` / `knowledge` 查询会
   基于旧记忆给出**看起来很正确**的答案。
5. **依赖怎么失效**。把「所有档案都标 STALE」最安全，但 STALE 一多就没人看；
   把「依赖变化」当成「文件改动」又会牵连无关产物。

## 决策

### 1. 草稿的目标路径是结构性的，不是约定的

`workflows/draft.py` 的 `_target_rel()` 拼出 `03_Manuscripts/Drafts/<CH>.md`，
然后**再校验一次**它不落在 `01_Canon` 下，违反直接抛 `SecurityError`。
落盘只走 `StagingArea.stage()`，那是全系统唯一允许 Agent 写内容的地方。

这不是「多加一道检查」，是让错误写不出来：路径由代码生成，不由调用方给。
想进正式区只有一条路：`approve` → `release prepare` → `publish`。

### 2. 写作之前必须有两份东西在手

- **规划够格**：`plan.check()` 逐项报 §10.2 的字段，缺「必须发生 / 禁止发生 /
  creative_scope」这类必需项就不许开写。不知道边界就动笔，写出来的东西没法判对错。
- **资料包 PASS**：复用最新一份 PASS 的 preflight；没有就现跑一次（不落盘）。
  BLOCKED 时拒绝，并把阻断项打出来。

### 3. 规划派生只取确定性可读的两处

真库章卡是散文式的：「## 必须发生的剧情事实」是一张时间表，
「## 禁止发生的内容」是一串列表项。`plan derive` 只做两件事：

- 表格第二列 → `must_happen`；
- 明确以「不得／禁止／不许／不能」开头的条目 → `must_not_happen` 与
  `creative_scope.forbidden`。

**`allowed` 与 `approval_required` 一律不派生。** 散文里没有对应来源，
编一个出来就等于替作者扩大了授权范围——而「扩大授权」正是这套系统要防的事。

写回时只插入原本不存在的键，写完校验正文逐字节未变；变了就回滚并报错。

### 4. 风险只能升，不能降

`deterministic_risk()` 命中死亡、复活、核心规则变更、身份揭露、RETCON 就至少 HIGH，
并把命中位置一并报出来（作者要能看到系统凭什么判 HIGH）。
人工与模型的调整只能往上抬，降级请求被忽略并留一条说明。

单字「死」会误伤「死路」「死寂」「死守」，所以命中后还要过一遍搭配过滤。
宁可漏判（`--risk HIGH` 能补），也不要让 HIGH 多到没人看——那样等于没有风险路由。

### 5. 高风险不许自审，返修有硬预算

- 审核角色与草稿角色相同时，`APPROVE` 直接抛 `SecurityError`，没有 `--force`；
- 每份 `REVISE` 算一轮，轮次用完就不再接受新一轮审核（抛 `ConflictError`）。
  顺序是「先判预算、再判资格、最后写记录」：反过来的话，预算耗尽的稿子仍会被
  写进一条 REVISE 记录，看起来像「还有人在正常推进」。

### 6. 正文批准要求先过审核

`approve text` 不是确认弹窗。它要求：审核结论是 APPROVE、按风险该过的角色都过过、
没有 OPEN 的 BLOCKER。不满足就拒绝并说清缺什么。

作者当然有权拍板，但「拍板」与「系统分不清拍板与随手点一下」是两件事。
要强行推进，走的是「改规划 / 换角色重审」，不是加一个 `--force`。

### 7. 记忆提案绑源哈希，发布前逐章问一句

- 提取的输入是**已批准候选**，不要求正文已 ACTIVE（PRD §15.1）；
- 提案里存 `source.sha256`（含 `staged` 路径）。正文改一个字节，`verify()` 判 `STALE`，
  `approve` 与发布都拒绝；
- `release prepare` 对每一章正文问一句：有已批准且未失效的提案，或有
  **作者显式写的「本章不产记忆 + 理由」**。两者都没有就阻断。

「没有提案」与「声明不产记忆」是两件事：前者是漏做，后者是决定。
混为一谈，闸门就退化成「没做也能过」。

需要单独发正文时，`--skip-closure` 是唯一的出口，且必须在命令行上写出来。
跳过时计划里记 `closure_skipped: true`，`release prepare` 与 `release show` 各打一行警告。
**这一条进计划的规范化 JSON，所以在作者批准的哈希里**——豁免不是口头约定，是批准对象的一部分。
字段只在为 `true` 时输出，0.11.0 及更早的计划重新序列化后哈希不变，
已批准待执行的旧计划不会因此变成「批准的是另一份计划」。

### 8. 依赖失效只波及相关产物

`dependencies.check()` 直接读 frontmatter 的 `depends_on`（权威在 Vault，不在索引）：

| 情形 | 结果 |
|---|---|
| 哈希一致 | `VALID` |
| 哈希不一致（HARD） | `STALE` |
| 哈希不一致（SOFT） | `NEEDS_REVIEW` |
| 没记 `content_hash`，或目标找不到 | `NEEDS_REVIEW` |

传递只走一级：A 依赖 B、B 自己 STALE 时，A 记 `NEEDS_REVIEW` 而不是 `STALE`。
索引里的 `dependencies` 表（v4 起填充）是同一份数据的派生视图，供查询用。

## 后果

**好的**：

- 「草稿进 Canon」「高风险自审」「半边发布」这三类错误在结构上写不出来；
- 审核预算与风险等级都是可数的、可复核的，不依赖谁记得；
- 依赖失效有了「不是全库一起红」的判据，STALE 才有信号价值。

**代价**：

- `write` 与 `proposal extract` 在没有真实模型适配器时只能靠 `--mock-response` 演练。
  这是有意的：不给默认路径，因为默认路径会在 staging 里留下一段占位正文；
- 已有发布测试要显式 `--skip-closure`，读起来像是「放水」。
  但它同时说明了一件事：**默认是拦的**；
- `review` 的规则检查只看形状（空正文、系统注释、拼文档、禁令专名）。
  人物认知边界、时间线一致性这类语义问题机器判不了，这一点写在每次的 findings 里，
  不假装查过。
