# ADR-014：批准绑定对象与当前字节；BLOCKER 不可豁免；RETCON 独立审批

- **状态**：已接受
- **批准人**：作者
- **日期**：2026-11-21
- **相关**：ADR-006（本篇细化它）、ADR-012

## 背景

T05 要做「审批、变更请求、影响分析」（PRD §14.2/§14.3/§14.5、§19、§20.3），
命令是 `novel inspect` / `approve artifact|proposal|release|change` /
`novel issue` / `novel change` / `novel impact`。

ADR-006 定的是「Agent 默认写 staging，作者最终批准」。到了要真发一章的时候，
那句话需要被拆成可以检查的条件，否则「已批准」只是一句口头同意。

## 问题

**一、批准的是任务，发布的是文件。** 「TASK-0007 已批准」这句话覆盖不了
「TASK-0007 的 staging 里现在装的是什么」。作者批完之后再往 staging 里塞一个
文件，仍然算「已批准」。

**二、批准之后改一个字节。** 作者看的是 A，发出去的是 A'。差一个标点也算改了：
MVP 不实现「这是不是实质修改」的判断，因为没有可靠的判据，而判断错的代价是
发出去的东西没人真看过。

**三、已知硬伤可以靠「豁免」进入正式版。** 如果 BLOCKER 能 `waive` 掉，
它就不是阻断级，只是一个颜色更红的提示。

**四、RETCON 混在普通档案修改里。** 「把某人改成没死」和「补一句天气」走同一条
审批，作者点一次头就同时同意了后者和前者的全部后果——而前者的后果写在正文里。

**五、签字基线会被判词污染。** 连续性签字绑正文 sha256。如果把问题单、变更单
放进正式区，每加一条判词就多一个签字失效源，改一次错别字要重签全书。

## 决策

### 一、批准有明确的对象类型

`approve` 的四个子命令对应四类对象，各自绑不同的东西：

| 对象 | 绑什么 | 为什么 |
|---|---|---|
| `artifact` | 候选文件的 sha256（或整包哈希） | 批的是要发布的那些字节 |
| `proposal` | 提案文件的 sha256 | 批的是下一版计划 |
| `release` | 发布计划的哈希 | 批的是这次要发哪些、按什么顺序 |
| `change` | **影响报告的哈希** | 批的是「我认了这个影响范围」 |

`target_type` / `target_id` / `target_hash` 三个字段落在批准记录里，
`for_target()` 按对象查历次批准，最后一笔有效即当前批准。

### 二、哈希按磁盘现算，不读 manifest

`inspect` 与 `approve` 都重新算 staging 文件当前的 sha256。manifest 是 stage
那一刻的记录，之后有人直接改 staging 里的文件它就过期了；拿过期哈希去批准，
批的是一份此刻已经不存在的字节。

manifest 与磁盘的差额不当作错误，而是作为 `drift` 报给作者看——**先让人知道，
再让人决定**。

### 三、复核走两道，各管一件事

`ApprovalStore.verify()` 逐文件比对（**包括文件消失**：`current` 里取不到也算
失效，`None` 不等于「没改动」）；`_approval_state()` 另外比对包哈希，防止
「文件都没变但候选集合变了」（比如 staging 里多了一个文件）。

两道闸门各有各的用例（`tests/unit/test_approvals.py` 打第一道，
`tests/integration/test_t05_cli.py` 打整条路）。删掉任意一道，对应的用例必须红——
这条验证做过，不是推测。

### 四、BLOCKER 不能豁免，只给两条路

`issue waive` 遇到 BLOCKER 直接抛 `ApprovalError`，报错里写明合法路径：

1. 修掉后 `issue resolve`，**必须写核验依据**（凭什么说它不再构成阻断）；
2. 或者先批准对应的规划/设定变更、缩小变更范围，让它不再成立。

`inspect` 同时扫任务 ID 与产物 ID 上的 OPEN BLOCKER——同一个问题可能记在任务上
（还没发布）也可能记在产物上（发布后才发现），只认一种就会漏。

### 五、RETCON 走独立路径，且必须有影响报告

```
DRAFT ──impact──> IMPACTED ──approve──> APPROVED
                       └────reject──> REJECTED
```

- 没跑 `impact` 就 `approve` → 拒绝（没有报告等于闭眼签字）；
- `--hash` 必须显式给出并与当前报告哈希一致（报告重新生成过就重新看）；
- 报告里有受影响正文，而作者既没 `--rewrite-chapters` 也没 `--narrow-scope` → 拒绝。
  PRD §19.3：只改档案不处理正文时**不能宣称 RETCON 完成**。缩小范围时把
  「仅改档案，受影响正文挂起」写进 `release_strategy`，让挂起是显式状态而不是遗忘。

另外，`blocking_scope()` 会拦「先改档案、后补变更」：只要有一笔未批准的 RETCON
覆盖了这批路径，普通文件审批就停下。否则独立审批只是一道可以绕过的装饰。

### 六、问题与变更存 runtime，不进索引

`<runtime>/issues/ISSUE-*.json`、`<runtime>/changes/CR-*.json`。

两个理由：

1. 它们是审核判词，不是作品内容。进正式区就被算进签字基线（见「问题五」）。
2. 索引必须是「Vault + commit」的纯函数。把 runtime 状态塞进 `issues` 表，
   同一个 commit 就能建出两个不同内容的库，T03 的验收「指定 commit 可独立构建」
   当场变成假的。所以 `issues` / `dependencies` 两张表**建了但空着**，
   并在 `rebuild-index` 输出里写明「建了不等于已支持」。

## 备选方案

| 方案 | 否决理由 |
|---|---|
| 批准绑定任务 ID（现状的简化版） | 换不了「批的是 A、发的是 B」这个问题 |
| 用文件 mtime 判「有没有改过」 | mtime 会被 checkout/同步改掉，且不区分内容 |
| 允许 `waive --force` 放行 BLOCKER | 等于取消阻断级；真要放行应当改设定或缩范围，让问题不再成立 |
| RETCON 与普通变更共用审批 | 作者点一次头就同意了正文层面的后果 |
| 问题单存 `02_Planning` | 判词进正式区，签字基线多一个失效源 |
| 问题状态进索引 `issues` 表 | 索引不再是 commit 的纯函数 |

## 影响

- **代价**：多一步 `impact`。RETCON 不能一句话走完，这是设计意图。
- **代价**：改一个标点就要重批。目前没有「非实质修改」白名单，留到 P1
  （`known_risks` 有记）。
- **收益**：`publish` 前能明确回答「批的是哪几个字节、现在还是不是那几个字节」。
- **约束**：以后新增可批准对象，必须同时定义它绑什么哈希；不接受「绑任务 ID」
  这种退让。
