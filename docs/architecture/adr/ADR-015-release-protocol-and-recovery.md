# ADR-015：发布是「先建完再切指针」，恢复靠交叉验证而不是取最新文件

- **状态**：已接受
- **批准人**：作者
- **日期**：2026-11-21
- **相关**：ADR-003（索引派生）、ADR-006（staging 后批准）、ADR-014（批准绑字节）

## 背景

T06 要做「发布与恢复内核」（PRD §17–§18），PRD §23 把它标成**安全里程碑**，
并写明「通过前不得把系统宣传为可用于真实正式发布」。

T05 之前的 `publish` 是一个覆盖动作：校验批准 → 把 staging 文件写到正式区 →
归档旧版。一次发布涉及 Markdown 文件、Git 提交、SQLite 索引三样东西，
覆盖式写法在正常路径上看不出问题，一旦中途失败就无法回答「现在正式版是哪一版」。

## 问题

**一、三样东西不可能塞进一个事务。** Markdown 在文件系统上，历史在 Git 里，
查询在 SQLite 里。想要「要么全成、要么全不成」，只能靠把三者包进一个更大的事务——
而那需要 Git 和 SQLite 共用一个 WAL，做不到。假装做到了，代价是崩溃后没人知道
发到哪一步。

**二、覆盖式发布的中间态就是「混合版本」。** 写到第 7 个文件时崩溃，正式区里
一半是新内容、一半是旧内容。这不是「可能发生」，是覆盖式写法的必然结果。

**三、恢复程序最容易被写成「取最新的那个文件」。** 指针、清单、日志都有时间戳，
看起来取最新的一定对。但正是崩溃会让时间戳失真：日志可能比指针新
（写了日志没来得及换指针），也可能比指针旧（换了指针还没来得及写日志）。
按时间戳猜，等于让崩溃点决定正式版是哪一版。

**四、锁用「文件年龄」判断死锁会放出第二个发布者。** 「超过 30 分钟就当它是残留」
在慢机器、长备份、网络盘上会直接把正在跑的发布踩掉。

**五、回退如果只是把指针拨回去，就没有任何记录说明「发生过什么」。**

**六、计划靠不住时批准就是橡皮图章。** 如果 `publish` 发现没有计划就临时生成一份
再当成批过，作者从没看过那份计划。

## 决策

### 一、先建完，再切换；正式版只有一个权威

22 步分成两段：**1–13 全在隔离快照里做**，第 18 步才动指针。

- 快照 = Vault 当前内容的一份完整复制（排除 staging / 审阅 / 归档 / 缓存 / `.git`）；
- 变更按**批准的精确字节**落进快照，逐条核对 sha256，不符直接失败；
- 在快照里 `git init` + 一次提交，得到本次发布的候选提交；
- 索引建在快照上；
- 清单（ReleaseManifest）写完后，才拿发布锁、再比对一次 base、写临时指针、
  fsync、原子替换。

正式版只由 `<runtime>/releases/active.json` 决定。它只有四个字段
（release_id / canon_revision / index_build_id / manifest_sha256），
写入走「临时文件 → fsync 文件 → fsync 目录 → `os.replace`」。

`index/active.json`（下次重建结果的指针）与 `releases/active.json`（正式版）
是两件不同的东西：前者随 `rebuild-index` 变，后者只在发布切换时变。
**查询优先读后者**，否则会出现「新发布 + 旧索引」的混搭。

### 二、计划与清单是两份记录，不能合并

| | ReleasePlan | ReleaseManifest |
|---|---|---|
| 何时产生 | 执行前 | 构建后 |
| 可变 | 是（重准备就换哈希，批准随之失效） | **否** |
| 证明什么 | 作者批的是这份计划 | 候选内容长这样，且只长这样 |

合并成一份的话，哈希要么在执行前算不出来（内容还没生成），要么在执行后
变成自引用（清单里记自己的哈希）。清单也**不写入它引用的 commit 的父提交**。
落盘用规范形式（键排序、紧凑分隔符、中文不转义），于是「文件字节哈希 ==
`package_hash(对象)`」，回执里记的哈希可以直接用 `sha256_file` 复核。

清单的不可变靠**写入方式**保证：`write_new`，已存在且内容不同就报冲突。
文件权限挡不住手改，所以 `release status` 每次都重算清单哈希与指针比对。

### 三、恢复靠四点交叉验证

`active_release` / ReleaseManifest / 事务日志 / 内容哈希，四者互相印证：

| 故障点 | 磁盘上的痕迹 | 判词 | 处置 |
|---|---|---|---|
| 切换前 | 日志停在 1–17，指针仍指旧版 | `OK` + 待续事务 | `resume` 或 `abort` |
| 提交后、索引前 | 日志停在 8–11 | 同上 | 同上 |
| 索引完成、切换前 | 日志到 17，候选完整 | 同上 | 同上 |
| 切换后、回执前 | 指针指向新版，回执缺失 | `RECEIPT_MISSING` | `repair` |
| 索引损坏 | 清单哈希对，索引哈希不符 | `INDEX_MISSING` | 重建或回退 |
| 指针损坏 | 读不出来 | `POINTER_CORRUPT` | 恢复模式，**不猜** |

`repair` 只在**指针确实指向该版且清单哈希对得上**时才补回执。补一张对不上账的
回执比没有回执更糟——它会让恢复程序以为一切正常。

### 四、锁由内核判定，不按年龄也不按 PID

`fcntl.flock(LOCK_EX | LOCK_NB)`。拿不到就抛，报错里带上持有人信息
（PID、主机、启动标识、任务、发布号、开始时间）供人判断。

锁文件里写持有人**只是给人看的**，不参与判定。要强制处理必须显式
`novel release unlock`，它会真的尝试获取一次：拿得到说明没人在用，
拿不到就拒绝，而不是删文件。

平台没有 `fcntl` 时直接拒绝发布（PRD §17.6 不支持未验证平台），
**不退化成「建个文件表示占着」**。

### 五、幂等靠编号，不靠运气

- `release_id` 在同一次发布的重试中不变；`txn_id` / `index_build_id` 由它派生，
  所以续做不会建出第二份索引；
- 索引编号显式传入时若已存在同名库，**报错而不是顺延**——顺延会让清单指向一个
  不存在的库；
- 已经在跑的发布重复 `execute`：只补回执与镜像，不再切换指针（`already_active`）；
- `publish --task` 遇到已 `done` 的任务直接拒绝：「再发一次新内容」是新任务，
  不是同一个任务重试。

### 六、回退是一次新发布；「复用旧版」用逐文件哈希担保，不用 commit sha

PRD §18.3 要求「复用已验证旧版 00_Canon revision 与索引」。

**索引复用是真的**：索引只是内容的函数，同样的内容建的库字节也相同，
`index_id_for(target)` 直接钉住旧库。

**commit sha 复用不了，我们也不假装复用它。** 每次发布都在自己的快照目录里
`git init` + 提交一次，sha 必然不同。把旧版的 sha 写进新清单，等于指向一个
在本版快照里不存在的提交——四点交叉验证当场对不上，恰恰制造出「混搭」。

替代做法是直接担保**内容**：

- 回退包的字节来源是旧版快照（`bytes_from=target`）；
- 清单逐文件写 sha256；
- 第 13 步前额外核对「本包文件集 == 目标版文件集」，多一个少一个不一样都拒绝，
  报错里列出具体路径。

这条比比对 sha 更严：sha 相同不代表内容相同（不同提交可以有同一棵树），
内容相同才是回退的本意。

回执强制写入三件事：这是一次新发布、原因是作者填的那句话、
**对外平台内容不在自动同步范围需人工处理**（PRD §18.3 末段）。
导致回退的那次发布记录不删。

### 七、镜像失败不撤销发布

第 21 步把内容镜像回 Vault 供 Obsidian 阅读。镜像失败只写进回执告警，
不撤销切换——正式查询读的是 `active_release` 与它的索引，不读这个镜像。
「已经切了但镜像没写」是**可接受且已记录**的状态；
「因为镜像失败把指针拨回去」反而会制造第二个不确定状态。

### 八、执行阶段不依赖任务记录还在

计划自带 `staged_paths`（目标相对路径 → staging 产物 Vault 内相对路径），
执行时按它取字节。任务 yaml 属于运行态，可能被清理；把它当成取字节的唯一依据，
清理过一次就再也续不了。

## 备选方案

| 方案 | 否决理由 |
|---|---|
| 覆盖式写入 + 先备份后回滚 | 中间态就是混合版本；回滚脚本本身也会崩 |
| 把 Markdown/Git/SQLite 包进一个事务 | 做不到，假装做到只是把不确定性藏起来 |
| 恢复时取「最新的那几个文件」 | 崩溃会让时间戳失真，正是最需要判断时最不可信 |
| 计划与清单合并成一份 | 要么哈希算不出，要么自引用 |
| 锁按文件年龄判残留 | 慢机器上会放出第二个发布者（PRD 明令禁止） |
| 无 fcntl 时退化成锁文件 | 假锁比没锁更危险：它给人「已保护」的错觉 |
| 回退 = 把指针拨回旧版 | 没有记录说明发生过什么，也无法标记依赖待复核 |
| 回退时复用旧版 commit sha | 指向本版快照里不存在的提交，交叉验证必然失败 |
| `publish` 找不到计划就临时生成 | 作者从没看过那份计划，批准变成橡皮图章 |

## 影响

- **代价**：发布从一步变成三步（`release prepare` → `approve release` →
  `publish`/`release execute`）。这是 PRD 要求的可审批对象，不是流程冗余。
- **代价**：每次发布复制一整棵 Vault。磁盘占用随发布次数线性增长，这是已知代价，
  换来「正式版永远对应一份完整、可复核、可回退的内容」。
- **代价**：改一个标点就要重新准备计划并重批（继承 ADR-014）。
- **收益**：任何一步崩掉，都能回答「正式版是哪一版、还差哪几步、能不能续」。
- **收益**：故障注入可测。`NOVEL_RELEASE_FAULT=before:18` / `after:18` 让断点
  变成回归用例，而不是靠人手工 kill 进程。
- **约束**：以后新增「会改变正式版」的动作，必须走同一套指针 + 清单 + 回执，
  不接受「就这一次直接写」。
- **约束**：`validate` / `integrity` 类校验在发布第 6 步只做了路径、字节、解析、
  正式区归属四样。Schema、ID、引用、依赖**尚未做**，`known_risks` 有记，
  不许在文档里写成已完成。
