# ADR-013：时间线用事件 DAG，状态按区间，认知与事实分表

- **状态**：已接受
- **批准人**：作者
- **日期**：2026-11-21
- **相关**：ADR-002、ADR-012

## 背景

T04 要做「时间线、事件、状态、认知」（PRD §9、§16.3、§20.2），命令是
`novel state` 与 `novel knowledge`。三条验收：倒叙查询要正确、排不出先后的
要返回 `UNORDERED`、角色误判不能污染客观状态。

这三条恰好对应三种最容易「看起来能用、实际在编故事」的做法。

## 问题

**一、章节顺序不是时间顺序。** 叙事可以倒叙、插叙、多线并行。拿
`chapter_no` 当时间轴，第 3 章写的可能是二十年前的回忆，一查「某人此刻在哪」
就会答成「二十年前他在哪」。这个错误没有报错、没有警告，只是答案悄悄错了。

**二、有些事件之间根本没有先后。** 两条线索互不相干，作者没写过它们谁先谁后。
系统要么承认「不知道」，要么按 ID 大小硬排一个——后者等于替作者编时间线，
而且编出来的顺序会被后续查询当成事实继续用。

**三、人物以为的事不是事实。** 「主角认为父亲已死」和「父亲已死」是两句话。
如果认知记录和客观断言放在同一张表里，某次查询忘了加过滤条件，角色的一次误判
就会变成世界的设定，并且再也查不出是哪一步污染的。

## 决策

### 一、事件存成有向图，比较靠可达性

`events` 存节点，`event_edges` 存先后。写入时把 `AFTER` 反向归一成一条边，
`SAME` 合并为同节点，只保留一个方向，避免同一事实存两遍、更新时漏一半。

`EventGraph.compare(a, b)` 只有三种结论：`BEFORE` / `AFTER` / `SAME`，
**没有路径就是 `UNORDERED`**。不按 ID、不按章节号、不按插入顺序兜底。

### 二、有环就报错，不静默取一个拓扑序

「A 在 B 前、B 在 C 前、C 在 A 前」说明设定自相矛盾。此时任何拓扑排序都是
在几个错误答案里挑一个，所以 `EventGraph.cycle()` 返回环上的节点，CLI 直接报
出来让人去改设定。**环不是排序问题，是数据问题。**

### 三、「最晚的一条」返回的是一批

`latest_among()` 求的是**极大元集合**（没有别的候选排在它后面），不是一个元素。
只有集合大小为 1 时才算唯一最晚；大于 1 说明这几条互不可比，调用方必须
返回 `UNORDERED`。

这条是 PRD §16.3「不得在 AMBIGUOUS 或 UNORDERED 时随意返回最新一条」的直接落地。
接口层面就不给「取第一条」的机会，比在每个调用点写注释可靠。

### 四、状态是区间 `[since, until)`

一次状态变更有生效事件 `since`，可选失效事件 `until`。查询
`--after X` / `--before X` 时按 X 与区间两端的关系判定命中，**左闭右开**：
开始事件本身算「已生效」，失效事件本身算「已失效」。

没有绑事件的记录（「天生失明」这类）视为恒成立，不当成缺数据。

### 五、认知与事实物理分表

`assertions` / `state_changes` 是客观事实，`knowledge` 是「谁在什么时候以为
什么」（带 `attitude`：知道 / 相信 / 怀疑 / 误信）。`state_answer()` 里
**不存在对 `knowledge` 的 select**，不是靠 `where kind != 'knowledge'` 过滤。

区别很重要：过滤条件会被后来的人改掉、会被 `select *` 绕过；表里没有这张表，
就绕不过去。验收第 3 条（角色误判不污染客观状态）测的就是这条物理隔离。

### 六、五个返回码不合并

`RESOLVED` / `NOT_RECORDED` / `AMBIGUOUS` / `UNORDERED` / `DISPUTED` 各有各的
补救动作：补记录、看多条候选、补事件先后、处理争议。合并成「查不到」之后，
作者不知道该补什么，Agent 会把「没记」当成「没有」写进下一章。

### 七、`02_Planning` 的语义记录不进事实表

章卡、细纲里的「计划发生」不是「已经发生」。索引只把 `01_Canon` 的
`Events/`、`Relationships/` 等正文派生记录进事实表，规划目录下的同类文件
单独计数（`skipped_planning`），在 `rebuild-index` 输出里显示。

## 备选方案

| 方案 | 否决理由 |
|---|---|
| 用 `chapter_no` + 场景序号当时间轴 | 倒叙一出现就系统性错误，且无法从数据上发现 |
| 用整数时间戳（第 N 年 M 月） | 虚构世界未必有统一纪元，作者也未必想定历法；强行要求等于增加写作负担 |
| 不可比时按 ID 排序取最后一条 | 排出来的顺序会被当事实继续使用，错误会传播 |
| 认知记录塞进 `assertions` 加 `kind` 字段 | 一处 `where` 写漏就污染客观状态，且污染后无法追溯 |
| 规划目录与正文混在一起建索引 | 「计划发生」被当成「已经发生」，与 Canon 准入判据冲突（v1.13） |

## 影响

- **代价**：作者要维护事件先后。不写 `event_edges` 时大量查询会落在
  `UNORDERED`——这是诚实的代价，不是缺陷。
- **代价**：`events`/`assertions`/`knowledge` 需要档案里存在对应记录才有数据。
  真库实测（2026-11-21）：事件 **7** 个（在 `05_Ledgers/Events/`，复合 ID
  `EVT-CH-0001-001` 形式），**边 0 条**，断言/状态变化/认知/揭示全为 **0**。
  所以任意两个事件的先后都是 `UNORDERED`，`state` 一律回答 `NOT_RECORDED`。
  **「表在」不等于「有数据」，「有事件」也不等于「有先后」**，两件事分开报。
- **收益**：倒叙、多线、误判三种情况各自有明确的返回码，而不是一个看起来正常
  的错误值。
- **约束**：后续任何「取最新一条」的实现都应当走 `latest_among()`，不要在
  SQL 里写 `order by ... limit 1`。
