# ADR-005：私人数据本地保存，不配置私人远端

- **状态**：已接受
- **批准人**：作者
- **日期**：2026-11-20
- **相关**：ADR-001、ADR-009

## 背景

作者的 Vault 里有完整作品：正文、设定、伏笔、记忆。这些内容一旦推到任何远端，
就多了一份自己无法彻底删除的副本（GitHub 的 fork、缓存、归档服务）。

旧系统已经发生过一次私人内容进入公共仓库并挂了三天的实例。

## 问题

完全不备份是不行的——硬盘会坏；全量推到云上又不可接受。矛盾点在「备份」与「发布」被混为一谈。

## 决策

- **私人 Vault 不配置任何远端**：`git remote -v` 必须为空；
- 不执行 `git push`，包括推到私有仓库；
- 不使用 Git 仓库作为唯一备份（见 ADR-009）；
- 备份是本地文件快照，位置在 Vault 之外、公仓之外；
- Vault 的 Git 只用于本地历史（可用于 diff 与回滚单个文件）；
- 若 Vault 已有 `.git`，保留并审计，不重新初始化。

## 备选方案

| 方案 | 为什么没选 |
|---|---|
| 推到私有 GitHub 仓库 | 多一份不可撤销的副本；账号被盗即全文泄露 |
| 加密后推远端 | 密钥管理成为新单点；且长篇小说改一次推一次，密文体积膨胀快 |
| 完全不用 Git，只靠快照 | 失去逐行 diff 与单文件回滚，作者手改冲突难排查 |
| 用 Git LFS 分仓 | 远端依赖仍在，没解决根本问题 |

## 影响

- 备份必须自己负责：`novel backup` 出清单 + sha256 + 回读校验，`novel restore` 先 `--dry-run`；
- 换机器要手动搬目录，没有 `git clone` 那么方便——这是有意的取舍；
- `novel doctor` 会检查 Vault 的 `remote` 配置，非空则报错。

## 残留风险

本地备份与原件同机，**抗不了整机损坏**。作者需自行定期把备份目录复制到外部介质。
系统不做这件事，也不假装做了。

## 补充（2026-11-20）：代码里同样不许留作品设定

上面每条讲的是「Vault 不推远端」。但**代码是推到公开仓库的**，所以还有第二条边界：
**公仓里的代码不许出现作品特有的名字与文案。**

这条被违反了两次，都是「模板里顺手写死」：

- `maps/jiuzhou.py`：地图页模板嵌了 12 项（世界名、三层行政示例、规则双链、界外设定说明）；
- `maps/admin.py`：区划表页的 title、aliases、官制双链嵌了 7 项。

两个模块的 docstring 都写着「代码里不留作品设定」，但**写的是意图，不是约束**——
没有任何检查会让它失败。

### 决策

1. 作品特有的一切——世界名、地名、人名、表名、页面文案、举例、双链目标——全部放
   `<project>/00_Project/<版式>.yaml`。当前段落：`naming`（名字与文件名）、
   `state_cities`（州城即府城的对应）、`page_notes`（页面上的补充文案与关联条目）、
   `special_states` / `special_kinds` / `anomalies` / `fu_notes`（界外与补记）。
2. 代码只认变量。配置缺了**不设默认值兜底**：能省就省掉那一段（如 `page_notes.links` 为空就不出「关联」条目），
   省不掉就报错（如 `naming.world` 缺失，`resolve()` 直接 `ConfigError`）。
3. **默认值也是设定**。`or "地图"` 这种兜底看似无害，一旦作品名改成别的，它就把旧名悄悄带回来。

### 检查方式（没有自动化）

用真库的实体名、别名、档案标题（2026-11-20 实测 902 个）反扫公仓全部文本文件。
**这个脚本故意不入库**——它要读的名字清单本身就是私人数据，进了公仓等于把清单交出去。

所以这是一条**需要手动重跑**的检查，不是 CI 门禁。代价写在 R-22 里。
