# ADR-009：备份与恢复策略

- **状态**：已接受
- **批准人**：作者
- **日期**：2026-11-20
- **相关**：ADR-003、ADR-005

## 背景

Vault 里是作者数年的设定与正文，其中很多内容**只存在于这一个目录**。
旧系统的备份是 `tar -czf` 一键打包，没有清单、没有校验，打包完不看里面有什么。

真实教训：一次目录迁移前做了快照，事后需要恢复某个文件时才发现
「打包时用了排除规则，恰好排除了要恢复的那个目录」。快照存在，但没用。

## 问题

备份的可信度不能靠「我打包了」，只能靠「我回读过并且逐字节一致」。
另外，恢复本身是危险操作——它可能覆盖作者刚写完的内容。

## 决策

**备份**

- 位置：`<runtime>/backups/<BACKUP-ID>/`，与 Vault 分离；
- 内容：全量文件 + `manifest.csv`（相对路径、字节数、sha256）；
- 写完立即**逐文件回读校验**，任何不一致即报失败，不产出「成功但有损」的备份；
- 默认不含 `.git`（`--include-git` 可选）；跳过缓存与临时文件；
- `novel backup --list` 列出历史备份与校验状态。

**恢复**

- 必须先 `--dry-run`，输出新增 / 冲突 / 损坏三类清单；
- 不覆盖现存文件；要覆盖需单独 `--overwrite` 且明确确认；
- 恢复前自动对当前状态再做一次快照，保证「恢复错了还能回去」；
- 只接受 `--as author`。

**边界**

- Git 不算备份：仓库与工作区同机，且历史可被改写；
- 本地备份也不抗整机损坏，作者需自行复制到外部介质；
- 系统不替你决定保留几份、保留多久。

## 备选方案

| 方案 | 为什么没选 |
|---|---|
| 只靠 Git 历史 | 同机、可被 `reset`/`filter-branch` 破坏，且大文件进 Git 会让仓库臃肿 |
| 增量备份（rsync 风格） | 实现复杂、链条长，恢复时依赖全部中间快照，反而更脆 |
| 直接复制目录（`cp -r`） | 无清单、无校验，不知道复制全了没有 |
| 备份到云端 | 与 ADR-005 冲突 |

## 影响

- 备份耗时与文件数线性相关（真实 Vault 约 5000 文件，秒级）；
- 磁盘占用随备份份数线性增长，清理由作者决定；
- 代价：每次备份要做两遍 IO（写 + 回读），换来「校验通过」这个结论可信。

## 验收方式

`tests/integration/test_backup_restore.py` 覆盖：备份后逐文件哈希一致、
删除文件后 restore 能找回、restore 默认不覆盖、`--dry-run` 不写盘。
