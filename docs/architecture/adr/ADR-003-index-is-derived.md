# ADR-003：索引可重建且不是事实源

- **状态**：已接受；**载体部分被 [ADR-012](ADR-012-sqlite-index-and-cjk-search.md) 取代**
  （`index.json` → SQLite 多 build；本篇「纯派生、可随时删、不反向写」的结论不变）
- **批准人**：作者
- **日期**：2026-11-20
- **相关**：ADR-002、ADR-009、ADR-012

## 背景

查询「某个人物出现在哪些章节」「某地属于哪个府」如果每次全文扫描，Vault 一大就慢到不可用。
旧系统曾用 SQLite 建索引，并同时把一些状态写进库里。

## 问题

一旦索引里存了「只有索引才有」的信息（如任务状态、签字状态、关系推导结果），
索引就变成了第二个事实源。它会与 Markdown 不一致，而且**修哪边都像对的**。

旧系统的实际状况：SQLite 8 张表，其中若干张存的是「事实」而非「缓存」；
删除索引会导致信息丢失，于是没人敢删——一个可重建物变成了不可删除物。

## 决策

索引 **只从 Markdown/YAML 派生**，删除后可完整重建，不允许反向写入事实源。

- 落盘位置：`<runtime>/index/index.json`，**不在 Vault 内**；
- 重建命令：`novel rebuild-index`；
- 字段：`path` / `project` / `id` / `type` / `status` / `title`，全部来自 frontmatter 或路径；
- 不索引 `07_Staging`、`08_Reviews`、`90_Archive`——运行态与归档不是当前事实；
- 冲突时以 Markdown 为准，索引无条件重建。

任务记录、批准记录、操作日志放在 `<runtime>/` 的其他子目录，与索引同级但**独立**：
它们本身是运行态数据，不进 Canon，也不参与 `validate`。

## 备选方案

| 方案 | 为什么没选 |
|---|---|
| SQLite 作索引 | 可用，但索引文件损坏时排查成本高；JSON 在十万条以内足够，且可肉眼比对 |
| 直接把索引写进 Vault | 污染事实源目录，备份与 Git 都会被噪音占满 |
| 常驻服务维护内存索引 | 引入进程与端口，违背「作者机器上长期无人值守」的前提 |

## 影响

- 索引随时可删，`rm -rf <runtime>/index` 是合法的排障手段；
- 重建耗时随文件数线性增长（真实 Vault 1087 份 md，单次秒级）；
- 代价：查询不能依赖索引里的「历史状态」，需要历史就去看 Git。

## 验收方式

`tests/integration/test_cli_flow.py` 覆盖「删索引 → 重建 → 条目数一致」；
CI 的 `guard` job 确认仓库内不出现 `10_Projects/` 等私人目录形态。
