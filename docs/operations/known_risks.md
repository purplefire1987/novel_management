## 一、能力缺口

## 二、数据问题（真实 Vault 内）

### R-04 `ASSET-0001` ID 冲突（成因已查明，待改号）

- **位置**：`04_Story_Assets/Settings/ASSET-0001_*.md`（2026-11-04，
  `import_batch: OUTLINE-20261104-0044`）与 `04_Story_Assets/Battles/ASSET-0001_*.md`
  （2026-11-05，`canon_status: deprecated`）。两份的标题都已在本文档里隐去。
- **成因**（旧系统 `99_Archive/legacy_v1/novel_system/src/novel_system/ids.py`）：
  `next_id()` 只做一件事——取索引里同 type 已有最大号 + 1（`next_serial`）。
  索引走 `entities_by_type()` 的 SQLite 查询，而 `entities` 表是 `PRIMARY KEY (id, type)`，
  **id 单列不唯一**，两条同 ID 记录能同时入表且无人报错。
  时间线：11-04 那份单篇先拿 0001；11-05 那批从 0001 重新起编，一路排到 0020

  文件系统路径判断）。任何写入路径都没做过「该 ID 已存在」的校验；`next_id()` 只保证
  「比索引里的最大号大」，而索引没收录的文件等于不存在。
- **新 CLI 曾经也看不见（已修，2026-11-20）**：`validate` 原先只扫 `CANON_KINDS` 六类，
  `04_Story_Assets` 不在范围，真实 Vault 上输出「重复 0 份」——是漏报不是干净。

  实测输出「实体 986 份（Canon 966 / 素材 21），重复 1 份」，退出码 1。
  **副作用**：真实 Vault 的 `validate` 从此失败，直到改号——这是它该有的样子。

  Battles 那份无人引用。
  **注意写入通道**：`04_Story_Assets` 属正式区，按硬约定不能手改，
  需要一条走 CLI 的改号入口（`novel renumber`）或作者手改后 `novel adopt` 收编。
- **已补的洞（2026-11-20，0.5.0）**：① 查重范围已扩到素材库 ✅；
  ② **分配前查存在性 + 加锁 + 审计**已到位（`novel allocate-id`）：

  锁文件防并发（PRD §8.1 禁止「无锁扫描最大号加一」）。

## 三、工程与流程

### R-06 本机 pytest 受沙箱限制

- 沙箱拦 `tempfile`，pytest 默认 basetemp 不可用；tempfile 还会回退到**当前目录**落随机名
  4 字节文件（内容 `blat`），跑一次脏一次。
- **可用跑法**：`PYTHONPATH=src python3 -m pytest -q -s -p no:cacheprovider --basetemp=.tmp/pt-<新名>`。
  两个坑：① `--basetemp` 必须是**尚不存在**的路径——pytest 启动时会 `rmtree` 已存在的 basetemp，
  而 rmdir 被沙箱拦，会直接 `PermissionError` 收集失败；② `-s` 不能省，否则 tempfile 探测提前炸。
- **2026-11-20 结果**：126 条用例全过（0 失败），含新增 `tests/integration/test_maps.py` 4 条。
- **待办**：真机终端再跑一次**不带** `--basetemp` 的完整 `pytest`，确认这套脚手架不是必需的。

### R-07 公仓推送通道

- 沙箱内的 HTTPS 代理无法连 GitHub（`CONNECT tunnel failed, 502`）。
- **已处置（2026-11-20）**：远端由 HTTPS 改为 SSH（`git@github.com:...`），
  `ssh -T git@github.com` 认证通过为 `purplefire1987`；`known_hosts` 里
  `github.com` 的主机公钥已存在且与密钥扫描结果一致。
- **残留**：SSH 只解决认证，不绕过耗时。若一次推送内容过大仍可能超时，
  可分两次推（先 `main`，再标签）。

### R-08 许可证已定

- 2026-11-20 作者拍板：**GPL-3.0-only**。`LICENSE` 为 gnu.org 官方全文，
  `pyproject.toml` 与 README 已同步，ADR-010 记录选择理由与未采纳方案。
- **影响**：代码可自由使用与商用；分发衍生作品须以同一许可开源。

### R-09 obsidian-git 未配置

- Vault 没有 `data.json`，即 obsidian-git 从未配置过，autoSave 未启用。
- **影响**：作者手改不会自动提交，需要手动 `git add/commit`，或者干脆不依赖 Git。
- **不擅自配置的原因**：自动提交会把「作者手改」与「CLI 写入」混进同一批提交，
  反而让 `adopt` 的基线判断变模糊。

## 四、结构性风险（设计取舍，不是 bug）

### R-10 备份与原件同机

- `novel backup` 落在同机磁盘，抗不了整机损坏。见 ADR-009。
- **缓解**：作者需自行复制到外部介质；系统不假装做了这件事。

### R-11 本地 Git 不算备份

- 私人 Vault 的 Git 只用于本地 diff 与单文件回滚，历史可被 `reset` 改写。

### R-12 断链检查依赖文件名索引

- `validate` 用文件名（stem）兜底解析双链，同名文件会产生歧义。
- **影响**：可能漏报真实断链，也可能把「指向另一个同名文件」当成已解析。
- **缓解**：`validate` 会同时报告重复 ID，范围是 **Canon 六类 + `04_Story_Assets`**（0.4.1 起）。
  仍不在范围内的目录（`02_Planning`、`05_Ledgers` 等若将来带 `id`）不会被查重——
  「重复 0 份」只等于「这两个范围里没有重号」，不等于全库无重号。

### R-13 隐私扫描只判形状，不判内容

- `scripts/privacy_scan.py` 能认出「私人目录形态」「真实档案命名」「本机路径」「凭据」，
  **认不出**「这段设定写的是我的书」。一段手打的人物小传只要不落在这些形状里，它扫不到。
- **实证一**（较早）：全仓扫过 0 发现之后，人工复核仍在三份文档里发现真实人物名与书名
  （拿来说明「id 与文件名错位」的例子直接用了真名）。已改成虚构的 `示例名` / `林砚`。
- **实证二**（2026-11-20，严重得多）：`maps/jiuzhou.py` 与 `maps/admin.py` 的页面模板嵌了
  **19 项**真实设定（世界名、三层行政示例、规则双链、界外说明、官制表名），
  `known_risks.md` 自己也有 5 项含**情节标题**。扫描器对这三处全部报 0——
  **已经在 `origin/main` 上**（0.4.1 起）。
- **影响**：扫描通过 ≠ 干净。CI 通过只说明「没有命中已知形状」。
- **缓解**：
  1. 形状类规则交给扫描器；内容类只能靠人工过，尤其是有没有用真名、真地名、真书名做示例。
  2. 内容检查的正确做法是**反扫**：从真库索引取实体名、别名、档案标题
     （2026-11-20 实测 902 个），逐个在公仓文本里找。脚本**故意不入库**——它要读的清单
     本身就是私人数据。所以它是**手动重跑**，不是门禁；动过 `maps/`、文档举例、
     测试夹具之后应重跑一次。
  3. 更根本的一条：**别在代码里写作品名**（ADR-005 补充条款）。凡是要写「某个地名」的地方，
     先问「它能不能从 `<project>/00_Project/*.yaml` 读」。写死之后再想清掉，代价是改历史。

## 五、与 PRD v2.1 的已知偏离（T02 引入，均有明确选择理由）

### R-14 编号位数：PRD 六位，实现四位

- PRD §8.1 的表与示例写 `CHAR-000001`（六位）；库内 986 份档案实际是 `CHAR-0001`（四位），
  `task_id` 例外，代码里就是 `TASK-%06d`。
- **选择**：新号一律**四位**，schema 的 pattern 放宽到 `[0-9]{4,6}` 以同时接受两种写法。
- **理由**：改六位要动全库文件名、frontmatter、所有 `[[双链]]`、canvas 节点，收益为零。
- **代价**：schema 不再能拦住「四/六位混用」。混用本身无害（ID 是字符串），
  有害的是「同一个号两种写法」，那由查重负责。

### R-15 通用元数据字段名未迁移

- PRD §8.2 要求 `artifact_type` / `artifact_status`；库内 966 份用的是 `type` / `canon_status`。
  PRD §8.3 还明令禁止再用一个 `canon_status` 混表产物状态／信息性质／审核状态。
- **选择**：`entity` schema 以现状字段（`type`/`canon_status`/`subtype`/`world`）为主，
  PRD 字段名作为可选字段并存，不强制择一。
- **理由**：T02 是「定义契约」，不是「迁移数据」。若按 PRD 严格实现，
  966 份档案会全部非法，`validate` 从「报 1 个重号」变成「报 966 份不合契约」——
  那是把治理问题伪装成验收失败。
- **代价**：两套字段名并存期间，schema 无法阻止有人只写 `canon_status` 不写 `artifact_status`。
  迁移属 T05/T07 的范围，做完才能收紧。

### R-16 两个模型的字段是推断出来的

- `transaction_journal` 与 `execution_receipt`：PRD §8.4 只列了类型名，
  §17.4（22 步执行序列）与 §18.2（崩溃恢复）给了语义，但**没有字段表**。
- **做法**：按 §17.4 的步骤号、§18.2 的「恢复程序基于 active_release / manifest /
  事务日志 / 内容哈希交叉验证」反推字段，并在两份 schema 的 `$comment` 里写明「推断」。
- **影响**：这两份契约可能与作者心里的模型不一致。T06 实现发布内核时应以实际需要为准，
  那时改 schema 是正常的，不算推翻本 ADR。
- **T06 结论（2026-11-21）**：四份 schema 与实现**字段完全对得上**，一处没改。
  但字段对得上不等于语义对得上——例如 `steps[].name` 用的是本实现的中文步骤名，
  PRD 只给了步骤号。现在有两条测试盯着这层契约：
  `tests/unit/test_release_model.py::test_records_satisfy_their_schema`（构造的）
  与 `tests/integration/test_t06_release.py::test_written_records_satisfy_schemas`（真落盘的）。
- 同理 `change_request`：§19.2 只给了中文条目，字段名由本实现命名；
  `revelation_mode` 因 PRD 只示例了 `EXPLICIT`，故意不设枚举。

### R-17 `02_Planning` 里 33 个 ID 形态不合法

- `IdRegistry.compounds` 在真实 Vault 上数出 **33 个**「看着像 ID、形态却不合 PRD」的标识：
  `EVT-CH-0001-001`（7 个事件）、`SCENE-CH-0001-001`（场景卡）、
  `VOL-0001-S1-DETAIL`（卷规划文档）、`LORE-20261104-000000`（导入批次）等。
- **影响**：它们不计入任何前缀的号段。`allocate-id --type EVENT` 会从 `EVT-0001` 起编，
  与既有的 `EVT-CH-0001-001` 不冲突（不同字符串），但**语义上是两套编号并存**。
  命令会提示「另有 N 个复合型 ID 以 EVT- 开头」，不会闷声发号。
- **不改的理由**：改号要动文件名 + frontmatter + 所有引用；而 PRD §8.1 同时禁止
  「仅以章节＋事件序号推导长期稳定 ID」，也就是这两种形态里只有一种能留。
  原计划「迁移属 T03（索引）与 T07（导入）」——**T03 已完成但没做这件事**：
  T03 的六项交付里没有 ID 迁移，本轮只做到「索引里能看见它们」。
  因此改号仍待 T07，或由作者单独裁定。
- **不要把它们当「不是 ID」**：一旦忽略，这些对象在查重时完全隐身。
  `is_compound_id()` 专门收这两类，就是为了让它们可见。

## T03 索引（0.6.0）

### R-18 历史 build 不自动清理

- 每次 `rebuild-index` 写 `index/builds/<build_id>.sqlite`，**不删旧的**。
  **真实 Vault 实测单份 11.5 MiB（12.1 MB）**（1067 产物 / 12867 块）。跑十次就是 115 MiB，
  一天反复调索引很容易堆到几百 MB——本轮调试就留下 5 份、共 62 MiB。
- **选择**：不自动清理。索引是派生物，删错了顶多重跑一次；自动删则要判断「哪份还在被读」，
  而这件事没有可靠答案（读者可能持有打开的文件句柄）。
- **代价**：作者要偶尔看一眼 `index/builds/` 并删掉不要的。`status` 会打「历史 build N 份」，
  算是提醒；但**它不报总占用**，堆到几百 MB 之前不会有人注意。
  彻底清理就是 `rm -rf <runtime>/index` 后重跑。
- **不做 LRU 的理由**：LRU 会在「刚切走的上一个 build」上误删——那正是最可能还要回滚回去的一份。
- **下次要补的**：`status` 报 `builds/` 的总占用，或者加一条 `index prune --keep N`。
  现在只能靠人记得。属 T03 之外的运维缺口，未做。

### R-19 块 ID 与行号绑定「这份文件当时的样子」

- `blocks` 表存 `block_id`（`p0001`…）与 `line_start`/`line_end`。它们是**生成那一刻**的坐标。
  作者手改正文后，同一 `p0001` 可能已经对应别的段落，行号也会整体偏移。
- **影响**：任何跨时间的引用（审阅意见写「p0042 那段有问题」、任务记录挂块 ID）
  在正文改动后就不可信了。**要引用就引「文件 sha256 + 块 ID」**，或者干脆引原文片段。
- **不做块级持久 ID 的理由**：正文是作者用 Obsidian 直接编辑的，没有插入点标记可言；
  想稳定就得往 Markdown 里塞锚点，那会污染正文，违反「正文只给人看」这条。
- 索引本身每次都从 Markdown 重来（ADR-012），所以库内一致性没问题，失效的只是**跨时间的引用**。

### R-20 索引不含 `02_Planning` 以外的语义表

- 17 张表里 **3 张是空表**（`foreshadowing` `dependencies` `issues`）。T04 之后
  `events` / `assertions` / `knowledge` 等六张已会填，但真库只有 `events` 有 **7** 行
  （`05_Ledgers/Events/`），`assertions` / `state_changes` / `knowledge` /
  `revelations` / `event_edges` 都是 **0** 行。
- **风险**：`SELECT * FROM knowledge` 得到 0 行，很容易被读成「这个人确实不知道这件事」，
  而实际是「这张表还没人填」。`state` / `knowledge` 因此一律返回 `NOT_RECORDED`，
  这不是 bug，也不是「世界设定里没有这件事」。
- **缓解**：`index_metadata.populated` / `empty` 分别声明「本版会填」与「建了不填」；
  `rebuild-index` 输出分三行打：会填的表、空表、以及语义表的**实际行数**。
  查询层看到 `NOT_RECORDED` 时必须读成「没记录」，不能读成「没有」（ADR-013）。

### R-21 索引范围包含 `00_System` 与 `90_Shared_Assets`

- 排除的是 `07_Staging` / `08_Reviews` / `90_Archive` / `99_Archive`（后两个是归档），
  但 `00_System`（23 份：策略、提示词、生成看板）与 `90_Shared_Assets`（17 份：模板）
  **仍然进索引**。真实库 1067 份产物里，这两块占 40 份。
- **影响**：`search` 会把 Agent 策略文档、Markdown 模板、Dataview 看板页一起端出来。
  已用结果分层把 `10_Projects/` 排到最前，所以正常查人名地名不会先看到它们；
  但搜「角色」「模板」这类词会命中模板正文。
- **这是待裁的问题，不是结论**。PRD §16.1 的 17 张表都是故事域语义，按这个口径
  `00_System` 本来就不该进；但「全库可搜」也有实用价值（查自己写的策略）。
  **本轮不改**：T03 的六项交付里没有「索引范围」这一项，擅自收窄会把「搜不到」变成新问题。
  作者裁定后再动，届时改 `skip_dirs_from_layout` 一处即可。

## T04 时间线（0.7.0）

### R-22 事件先后要人手写，不写就一律 `UNORDERED`

- `event_edges` 只能从档案里的显式先后关系提取。作者没写「A 在 B 之前」时，
  `EventGraph.compare()` 给出 `UNORDERED`，`state --after X` 会把这类记录留在
  候选池外，最终返回 `UNORDERED` 或 `NOT_RECORDED`。
- **真库当前就是这个状态**：7 个事件、0 条边。每个事件的 frontmatter 有
  `chapter_id` 与 `sequence`，但 `sequence` 的语义（叙述序还是故事序）没有定义，
  **按它连边等于替作者判定倒叙**，所以不连。CLI 在 `UNORDERED` 时会明说
  「事件图有 7 个事件、0 条先后关系」，避免被读成「系统坏了」或「两者同时发生」。
- **这不是缺陷，是唯一诚实的选择**：按 ID 或章节号硬排会替作者编时间线，
  而编出来的顺序会被后续查询当事实继续用，错误会传播（ADR-013）。
- **代价**：想用 `state` / `knowledge` 查得准，就得付出维护事件边的成本。
- **不做「大致按章节序」兜底的理由**：倒叙一章就能让整条时间轴错位，而且错了不报错。

### R-23 认知记录依赖作者显式登记

- `knowledge` 表要的是「谁在什么时候知道/相信什么」，这没法从正文自动推——
  推出来的是猜测，而猜测一旦入库就会以「系统认为」的身份出现。
- **风险**：不登记时 `knowledge` 一律 `NOT_RECORDED`，容易被读成「他不知道」。
- **缓解**：CLI 输出把 `NOT_RECORDED` 解释成「没有记录」，并明确写出「不等于不知道」。

## T05 审批与变更（0.8.0）

### R-24 影响报告是「提及」级判断，不是语义级

- `impact` 用「块文本里出现目标 ID / 实体名 / 别名」来找受影响正文。它是**宁多勿漏**
  的粗筛：名字重名会误报，代词指代（「他」「那人」）会漏报。
- **影响**：`affected_chapters` 可能多列几章，也可能漏掉只靠代词指代的那几章。
  报告是给作者看的清单，不是自动改写的依据。
- **为什么这样也算够用**：RETCON 闸门要的是「作者必须看一眼受影响正文并明确表态」，
  粗筛能保证这一点；精确到段落的语义归属需要 T08 之后的实体识别，本版不做。
- **缓解**：`notes` 里会说明目标有没有实体档案（没有时只剩 ID 匹配，可能偏少），
  mention 里记下命中的词与类型（`name` / `alias` / `id`），便于人工核对误命中。

### R-25 批准按「改一个字节就失效」，没有非实质修改白名单

- PRD §14.5 要求批准绑定内容指纹。本版不做「这是不是实质修改」的判断：
  改一个标点也要重新批准。
- **代价**：作者手改一个错字后要重走 `inspect → approve`。
- **不做白名单的理由**：MVP 没有可靠的「实质」判据，判错的代价是发出去的东西
  没人真看过。白名单留到 P1，届时也必须由作者显式开启。

### R-26 「最近一次批准」按记录顺序取，不按时间戳排序

- `ApprovalStore.latest_for()` / `for_target()` 取的是按文件名排序后的最后一条。
  文件名是 `APR-00000N` 递增，正常情况下等价于「最新」。
- **风险**：手工复制旧批准文件、或从备份恢复单个文件，会让编号与时间顺序不一致，
  此时「最近一次」可能取到较旧的那笔。
- **当前不修的理由**：修法是按 `approved_at` 排序并处理同一秒的并列，属健壮性改进，
  不在 T05 验收范围内。**已知且记录在案**，恢复备份后建议整目录一起恢复。

## T06 发布与恢复（0.9.0）

### R-27 每次发布复制整棵 Vault，磁盘线性增长

- 第 4 步把 Vault 复制成隔离快照（排除 staging / 审阅 / 归档 / 缓存 / `.git`），
  发布 N 次就有 N 份快照，放在 `<runtime>/releases/<REL>/snapshot/`。
- **为什么接受**：换来「正式版永远对应一份完整、可复核、可回退的内容」。
  就地改的代价是崩溃后出现混合版本（PRD §17.1 的底线）。
- **代价**：真实 Vault 的正式区约千份档案，单份快照就是几十 MB 量级；
  频繁发布需要人偶尔看一眼 `releases/` 并清理已 `SUPERSEDED` 的旧快照。
- **未做**：没有 `release prune`。清理与 R-18（索引不自动清理）同理——
  自动删要判断「哪份还在被引用」，而这件事没有可靠答案。
  **注意**：被回退复用索引的那份快照不能删，删了那次回退就续不上。

### R-28 第 6 步校验只做了四样

- PRD §17.4 第 6 步写的是「校验路径、哈希、解析与审批」。实现里只做了：
  目标在正式区、候选字节哈希与计划一致、Markdown 能解析、路径不越界。
- **没做的**：JSON Schema 校验、实体 ID 合法性、双链引用可解析、依赖表核对。
  `validate` 命令会做前两样，但**发布路径没有调用它**。
- **后果**：一份 schema 不合契约的档案可以正常发布出去，直到有人跑 `novel validate`。
- **不做的理由**：T07/T08 之前没有依赖表；把 `validate` 塞进发布路径会让
  「存量 966 份里有一份重号」直接卡死所有发布——那是把治理问题伪装成发布失败。
- **缓解**：发布后回执与输出都提示重跑 `validate` 与 `rebuild-index`。
  这条必须在文档里留白，不能写成「发布已校验全部契约」。

### R-29 回退不复用旧版 commit sha（偏离 PRD §18.3 字面）

- PRD §18.3 要求「复用已验证旧版 00_Canon revision 与索引」。
- **索引是真复用**：`index_id_for(target)` 直接钉住旧库，不重建。
- **revision 不复用**：每次发布都在自己的快照目录里 `git init` + 提交一次，
  sha 必然不同。把旧 sha 写进新清单会指向一个在本版快照里不存在的提交，
  四点交叉验证当场失败——那正是 PRD 要防的「混搭」。
- **替代担保**：第 13 步前核对「本包文件集 == 目标版文件集」，逐文件 sha256 比，
  多一个少一个不一样都拒绝并列出路径。比比对 commit sha 更严
  （不同提交可以有同一棵树，sha 相同不代表内容相同）。
- **判断依据**：ADR-015 第六节。若作者认为必须字面复用 revision，
  需要先决定「快照是否共享同一 Git 仓库」，那是另一套设计。

### R-30 发布锁不跨主机

- `flock` 的互斥范围是「同一台机器上的同一份文件」。Vault 放在网络盘、
  或两台机器同时挂着同一个 runtime 时，锁不保证互斥。
- **当前适用前提**：单作者、单机、runtime 在本地磁盘（ADR-004/005 的前提）。
- **缓解**：`release unlock` 会告知当前锁的持有人与主机名，跨机冲突时能看出来；
  系统不假装提供了分布式锁。

### R-31 故障注入只覆盖步骤边界，不覆盖「写到一半断电」

- `NOVEL_RELEASE_FAULT=before:N` / `after:N` 在步骤**前后**抛异常，
  模拟的是进程在两步之间死掉。
- **没覆盖**：单个文件写一半、`os.replace` 执行到一半、`fsync` 返回前断电。
  这些靠的是「写临时文件 + 原子替换」这一层保证，而不是靠故障注入验证。
- **代价**：真正的掉电场景只能在真机断一次电才验得了。本轮**没做**这个实验，
  所以就「掉电安全」这件事，只能说设计上依赖原子替换，不能说已验证。

### R-32 回退依赖旧索引还在

- 回退要复用旧版索引库 `index/builds/<IDX>.sqlite`。它被清理过（R-18 提到
  `index/builds/` 会堆、作者可能整目录删）时，回退会直接拒绝：
  「旧索引被清理过，这次回退无法复用」。
- **为什么拒绝而不是重建**：重建得到的是新库、新字节哈希，那份「已验证的旧索引」
  就不存在了。此时要么接受「回退但索引是新建的」，要么先补救——这是作者的决定。
- **缓解**：错误信息写明「无法复用，请改为重新构建」。重建路径尚未提供开关，
  需要手工改 `plan.meta.json`，属未完成的便利性。

### R-33 `publish` 从一步变成三步

- 0.9.0 起必须 `release prepare` → `approve release` → `publish`。
- **代价**：日常发布多两次命令；忘记第二步会得到码 4。
- **为什么不是冗余**：PRD §17.2 要求批准对象是 ReleasePlan，
  而「计划」只有生成出来才存在。省掉它，批准就只能绑任务——那正是 ADR-014 否掉的。

## T07 原稿导入（0.10.0）

### R-34 只认 UTF-8，不猜编码

- GBK / GB18030 / Big5 文件一律拒绝，报「请先转成 UTF-8 再导入」。
- **代价**：老稿子要做一次转换，转换工具在 Windows 记事本里都自带，但要人来点。
- **为什么不做自动识别**：识别靠猜。猜错的形态是「成功导入，少了几百个字」，
  不报错、不可查。宁可让作者转一次码，也不换一个静默坏掉的底稿。

### R-35 只抽「ID 形态」的候选提及，人名类要先有档案

- 提取词典来自项目 Canon 里的 `name` / `aliases`。Canon 里没有可用的名称/别名
  （新起的项目、或正文还没进去的项目）时，词典就只认得 `CHAR-0001` 这种 ID 形态的提及。
- **代价**：写「张三走进来」的旧稿，第一章就会被报成「待提取」。
- **这不是缺陷而是边界**：没有实体档案就没有名字可比对，凭空拟一份人名表
  等于替作者做设定决定。报告里写明这一点，`chapters_pending` 逐章列出。
- 提取覆盖**不阻断发布**——「这章没提到人名」不该变成「这章不许进正文」。

### R-36 抽样只测定位准确率，不测语义提取

- `sample_result.accuracy` 的定义是「定位符能否反查回原文」，100% 只证明坐标对。
- **误读风险**：把它当成「提取正确率」会得出「全库已完整」的错误结论，
  而 PRD 末句专门禁止这个推论。
- **缓解**：口径写死在 `note` 里，同时进 `known_limits`，`report` 每次输出都带着。
  语义正确性只能人工核，系统不代劳。

### R-37 一行一行的定位符在「文件被改过」后失效

- 定位符 `旧稿.md#L3-L9` 指向**导入当时**那份原始字节。归档区里那份不会被改，
  所以定位始终有效；但如果作者绕过系统直接改了归档里的原稿，行号就可能错位。
- **为什么会错位**：行号是「文件的行」，不是「内容的哈希」。省掉哈希是为了让人
  能肉眼核对，代价就是它不是内容绑定的。
- **缓解**：`raw_bytes_preserved` 与逐份回读 sha256 保证归档那份就是导入当时那份；
  归档区不在正式区，正常流程不会写它。

### R-38 分批发布的中间态

- 五章分三批：前两批发布后，正式区是「部分正文」，台账里第三批仍写「尚未发号」。
  这是**如实记录**，不是错误状态。
- **风险**：此时若有人直接读正文当全稿，会漏掉未发批次。台账与 `import report`
  都写明未完成，但没有任何机制阻止误读。
- **为什么不分批一次性发完**：上百章一次批完，作者实际不会逐章看，
  批准就变成了盖章。分批是让「批」这个动作有内容。

### R-39 换切分方式不能重分批

- 已发号的批次记录在 `assignments.json`。用不同 `--batch-size` 重跑同一批会被拒绝。
- **代价**：想改分批只能开新的导入号（`import scan` 再来一次）。
- **为什么拒绝而不重算**：重算会让已发出的 CH 号与章对不上，
  而那些号可能已经发到了正式区。

### R-40 不带 `--project` 时查重口径偏严

- `allocate-id` 不带 `--project` 时无法确定项目布局，退回「全库皆正式区」的口径，
  于是 Vault 根的旧归档（`99_Archive/legacy_v1`）里与正式区同号的会被算进来。
  真库实测：不带 `--project` 报 2 个重复，带上报 1 个——**差的那一个是历史归档副本，不是真撞号**。
- **为什么不推断项目**：本系统一贯不按「只有一个项目」推断写作用哪部书（README §4 有说明）。
  查重不是写入，但为它单独破例会让「什么时候会推断」变得说不清。
- **缓解**：输出里明说「口径从严，数可能偏多」，并提示加 `--project` 得到准确数。

## T08 Agent 与写前资料包（0.11.0）

### R-41 权限矩阵有三份副本，只有两份在比对范围里

- 副本一：PRD §6.1 的 A1–A9（已按规范 v1.7 §4 作废）；副本二：人读版
  `agents/common/permissions.md`；副本三：`agents/registry.py`。
- 测试逐格比对的是**副本二与副本三**。副本一（PRD 原文）没有参与比对——
  它已经作废，留着只作史料。
- **残留风险**：若将来有人照着 PRD 原文改 md 表格，测试会红（好事）；
  但若有人只改 PRD 原文而不改代码，**没有任何机制报警**。
- **缓解**：`agents/common/permissions.md` 顶部写明「本表是机器副本的来源，
  改这里必须同时改 `registry.py`，否则测试红」；ADR-017 记了这条边界。

### R-42 提示词是建议，真正拦住越权的是工具网关

- 九份提示词里有「范围与写入边界」「不得宣称未执行的动作」两段，但那都是**文字**。
  模型完全可以无视它们，说出「已写入第 12 章」。
- 拦住它的是执行层：`ToolContext.call()` 先查能力位、`SCOPE_AUTHORIZED` 必须给 scope、
  写 Canon 与发布两个方法永远抛 `SecurityError`。**模型说什么不重要，它能调什么才重要。**
- **残留风险**：模型可以在**文字里**宣称做了没做的事。这不是代码能拦的，
  只能靠「所有落盘动作都由 CLI 记账」来反查——`ops.jsonl` 里没有的操作就是没发生。

### R-43 token 按「非空白字符数」估，中英混排会偏

- `estimate_tokens()` 数的是非空白字符。中文一个字符约等于 1 token 上下，
  英文一个词约 1.3 token，代码块与 JSON 的符号密度更高。
- **代价**：预算按字符算，实际 token 可能多出两三成。`--budget` 给的是**安全下限**，
  不是精确值。
- **为什么不接 tokenizer**：那要引一个模型相关的依赖，而本包一贯零运行时依赖
  （ADR-011 同一条理由）。宁可把预算留宽，不让「估得准」变成一个装不上的依赖。
- **缓解**：`--output-reserve` 与 `--hard-reserve` 默认就给得偏大；
  装不下时是 `BLOCKED` 而不是静默截断硬约束。

### R-44 老索引读不到伏笔，preflight 会 BLOCKED

- `foreshadowing` 从索引第 3 版（`BUILDER_VERSION` 0.11.0）起才会填，且这一版给表加了
  `window_policy` / `window_end` / `reveal_scope` 三列。用第 2 版建的库，表在、列不全。
- **初版的两种错法都试过**：先是直接 `select window_policy` → `sqlite3.OperationalError`
  堆栈刷屏（真库实测撞到，作者看到的是「程序坏了」）；补上容错后变成静默返回 0 条，
  于是「未回收伏笔 0 条」看起来像「这本书没有未回收的伏笔」——后者更危险。
- **现在的行为**：表缺列时按空列读（行还在，窗口信息诚实留空），`supported=False`，
  `preflight` 记一条 **BLOCKER**（`RULES`），消息写「未回收承诺这一整类硬约束本次无法检查，
  等于没做——先 `novel rebuild-index` 再跑 preflight」，`gate_result=BLOCKED`。
  终端与 YAML 都能看到。
- **为什么不放行**：「这一类没查」与「这一类没问题」必须是两个结论。
  前者放行等于让一次「什么都没检查」的 preflight 拿到 PASS。
- **为什么不在读的时候自动重建**：建索引要几十秒到几分钟，让一个「查资料」的命令
  顺手改索引，等于把只读命令变成写入命令。
- **升级步骤**：真库升级后**必须跑一次 `rebuild-index`**。CHANGELOG 0.11.0、README、
  `getting_started` 的排错表都写了这一条。

### R-45 没有章卡就没有资料包

- `creative_scope` 缺失判 `SCOPE` 阻断，规划文档缺失判 `PLANNING` 阻断。
- **代价**：新项目第一次用 `preflight` 一定 BLOCKED——因为还没写章卡。
  这不是 bug，是「先想清楚这一章要干什么」被做成了硬前置。
- **为什么会让人困惑**：`BLOCKED` 看起来像「系统坏了」。输出里明说该补哪个文件、
  放在哪个目录（`02_Planning/Chapters/CH-xxxx.md`，frontmatter 带 `id` 与
  `creative_scope`）。
- **为什么不放行**：没有创意范围就没有「禁止发生」的清单，此时生成的资料包
  必然把「什么都可能」当成默认，等于白做。

### R-46 模型提炼的约束不稳定，只有失败路径是确定的

- 未接模型时，`key_constraints` 完全来自规划原文，逐字照录，可复现。
- 接了模型且成功时，模型会**合并、改写、补出**若干条约束。同一份章卡跑两次，
  条数与措辞可能不同。
- **缓解**：`model.used` 与 `added_constraints` 逐条列出「哪几条是模型加的」，
  作者能自己判断要不要信；模型失败（非 JSON / 缺字段 / `role` 写错）就整体退回原文，
  记一条可读 issue，绝不「尽力而为提取字段」。
- **残留风险**：成功那次仍然是模型判断。要绝对可复现就别给模型。

### R-47 计量记的是用量，不是钱

- `<runtime>/usage/YYYYMMDD.jsonl` 记 prompt / completion tokens、调用次数、耗时、成败。
- **它回答不了「这个月花了多少钱」**：单价随模型与时段变，而单价写进代码就会过期。
- **为什么不折算**：一个会过期的换算率，比一个没有换算率更误导。
  要算钱就拿 token 数乘当下的官方单价，那一步该在系统之外做。
- **替代它的一件小事**：`by_role` / `by_tool` 能回答「哪个角色在烧钱」，
  这通常比总额更有用。

## T09 写稿与审核（0.12.0）

### R-48 写稿没有真实适配器，只能喂 `--mock-response`

- 本期 `novel write` 只接受从文件读入的模型输出，不接任何真实 API。不给就直接报错。
- **这不算缺陷**：真正的写作发生在 Agent 侧，`write` 的职责是「把一份模型输出合规地
  落到 staging」，那部分已经完整可测。接真适配器只是换掉输入来源。
- **但要知道**：现在无法用一条命令从章卡直接生成草稿。要自动化，得在 Agent 侧串
  `preflight` → 模型 → `write --mock-response`。
- **为什么不提供「空草稿」兜底**：一份看起来像正文的占位稿，比一个明确的报错更容易
  被当真，最后会有人拿它去审核。

### R-49 规则检查只判形状，语义问题每条写一句「判不了」

- 机器能查四类形状：空正文、正文里混入系统注释标记、正文里出现第二份文档
  （`---` 分隔线）、禁令条目里点了名的专名出现在正文里。
- **它查不了**：人物用了还没获得的信息、时间线倒错、称谓前后不一致、语气崩坏。
- **缓解方式不是「尽量查」，是明确认输**：一条 findings 都没有时，必写一条
  `SUGGESTION` 说「机器只查了形状……语义问题机器判不了，需要专项角色与作者过目」。
  有 findings 时不加这条——真问题已经在列表里了，再塞一条底噪会把它压下去。
- **残留风险**：两条路都不等于「语义过了」。看到 `APPROVE` 就以为万事大吉，
  是这个设计最容易被误读的地方。

### R-50 返修预算只数「判过 REVISE 的轮」，`PARTIAL` 不消耗预算

- `rounds_used` 的口径是：历史记录里 `verdict=REVISE` 的**轮号去重计数**。
- 好处是同一轮多个审核人都判 REVISE 只消耗一轮，不会因为人多而提前耗尽预算。
- **缺口**：一直交不出齐角色的稿子（每轮都是 `PARTIAL`）永远不消耗预算，
  可以无限拖下去。T09 验收第三条「超过返修预算停止」在语义上成立，但拦不住这种耗法。
- **为什么不把 `PARTIAL` 也算一轮**：`PARTIAL` 可能是「另一个角色还没排上」，
  不是稿子的问题，算进去会误伤正常流程。真要堵，靠的是任务看板上的停留时间，
  不是把审核计数做成计时器。

### R-51 审核结论、提案、依赖状态都在 runtime，不在 Vault

- 全部存 `<runtime>/reviews/`、`<runtime>/proposals/`，`deps` 直接读 Vault 的
  frontmatter 但状态是现算的。
- **换机器 = 看不到审核历史**。Vault 可以搬，runtime 搬过去也能用（路径相对），
  但两个 runtime 不会互相同步。
- **为什么不做进 Vault**：审核记录进正式区就会被算进连续性签字基线，也会让
  索引不再是「Vault + commit」的纯函数——与 issues / changes 同一理由。

## T10 记忆与共同发布（0.12.0）

### R-52 `proposal declare-none` 能合法绕过共同发布闸

- 只要写了理由，作者可以宣布「本章不产记忆」，闸门就放行。
- **这是设计，不是漏洞**：过渡章、纯动作章确实可能不产记忆。要禁止等价于
  强迫作者编一条假记忆。
- **实际的风险是「批量宣布」**：一章一章写理由很累，`--reason "同上"` 就能过。
  闸门拦不住敷衍，只拦得住「没人说过」。
- **可查的部分**：`deps closure` 会把每个 `declare-none` 的章节和理由都列出来，
  要复核就整批看，而不是一章章看。

### R-53 依赖传递只走一级，深层失效会显示成「不需要处理」

- A 依赖 B、B 依赖 C，C 变了：B 判 `STALE`，A 判 `NEEDS_REVIEW`，再往上一层
  就不再传。
- **代价**：链越长，越上层越可能停在 `VALID` 而实际已受影响。
- **为什么不做全量传递**：一次局部改动会让整本书变成「需要复核」，STALE 多到
  没人看，等于没有。分级不是为了准确，是为了**让人还愿意看**。
- **补法**：`deps show` 看单条链路；真要全图，看 `impact`（T05 的影响报告）
  而不是依赖状态。

### R-54 索引里的 `dependencies` 表可能是上一轮的

- `dependencies` 表从索引 v4 起会填，但 `deps check` **不读它**——直接读 Markdown。
- 所以状态永远是最新的，但**索引里的那份可能过期**，用它做统计会得到旧数。
- **为什么允许这种不一致**：索引是「Vault + commit」的纯函数，它只能反映建库那一刻。
  让 `deps check` 顺手重建索引，等于把只读命令变成写入命令（与 R-44 同一条理由）。

### R-55 真库章卡还没有 `creative_scope`，`plan derive` 也补不全

- `plan check CH-0001` 在真库上报「还缺 1 项必需字段：创作授权（creative_scope）」，
  因此 `write` 会拒绝开写、`preflight` 会判 `BLOCKED`。
- `plan derive CH-0001 --write` 能补 `must_happen` / `must_not_happen` /
  `creative_scope.forbidden`（共 10 + 5 + 5 条，各带回溯定位符）。
- **`creative_scope.allowed` 与 `approval_required` 补不了**：散文里没有这两项的来源，
  派生等于替作者扩权。这两项必须作者自己写。
- **状态**：现在补完禁止项之后，章卡仍会判「缺必需字段」，直到作者手写 `allowed`。
  这不是 bug，是这一项本来就不该由机器代笔。

### R-56 发布第 8 步曾把刚建好的快照删掉重建（**已修，0.12.1**）

- 现象：`execute` 第 4 步 `copy_tree(vault → snapshot)`、第 5 步写变更、第 7 步核文件集，
  第 8 步又调 `build_snapshot()`，它第一件事是 `if dest.exists(): shutil.rmtree(dest)`，
  然后从头复制 + 应用 + 提交 —— 前三步的成果被作废重做。
- 代价：每次发布多一次全量删除 + 全量复制（真库 1000+ 文件）；
  且在禁止删除的环境里必炸在 `rmtree` 上，哪怕前面七步都已成功。
- **修法（已落地）**：第 8 步只调 `commit_snapshot(snapshot, release_id, plan.hash)` +
  `write_atomic(revision_path, ...)`；`build_snapshot` 与只被它使用的 `SnapshotResult`
  一并删除，免得下次又有人走回去。
- **验证**：T06 19 个用例全过；全量 658 用例 0 失败；selfcheck 50/50。
- **残留**：`build_snapshot` 的 docstring 里那句「任一步失败都不留半个候选」不再有对应实现——
  现在由 4/5/7 步各自负责，失败时靠 journal 与 `resume`/`abort` 收尾，不再整体回滚快照。
