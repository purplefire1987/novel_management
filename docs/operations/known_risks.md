## 三、工程与流程

### R-06 本机 pytest 受沙箱限制

- 沙箱拦 `tempfile`，pytest 默认 basetemp 不可用；tempfile 还会回退到**当前目录**落随机名
  4 字节文件（内容 `blat`），跑一次脏一次。
- **可用跑法**：`PYTHONPATH=src python3 -m pytest -q -s -p no:cacheprovider --basetemp=.tmp/pt-<新名>`。
  两个坑：① `--basetemp` 必须是**尚不存在**的路径——pytest 启动时会 `rmtree` 已存在的 basetemp，
  而 rmdir 被沙箱拦，会直接 `PermissionError` 收集失败；② `-s` 不能省，否则 tempfile 探测提前炸。
- **2026-11-20 结果**：126 条用例全过（0 失败），含新增 `tests/integration/test_maps.py` 4 条。
- **待办**：真机终端再跑一次**不带** `--basetemp` 的完整 `pytest`，确认这套脚手架不是必需的。

### R-07 公仓推送通道

- 沙箱内的 HTTPS 代理无法连 GitHub（`CONNECT tunnel failed, 502`）。
- **已处置（2026-11-20）**：远端由 HTTPS 改为 SSH（`git@github.com:...`），
  `ssh -T git@github.com` 认证通过为 `purplefire1987`；`known_hosts` 里
  `github.com` 的主机公钥已存在且与密钥扫描结果一致。
- **残留**：SSH 只解决认证，不绕过耗时。若一次推送内容过大仍可能超时，
  可分两次推（先 `main`，再标签）。

### R-08 许可证已定

- 2026-11-20 作者拍板：**GPL-3.0-only**。`LICENSE` 为 gnu.org 官方全文，
  `pyproject.toml` 与 README 已同步，ADR-010 记录选择理由与未采纳方案。
- **影响**：代码可自由使用与商用；分发衍生作品须以同一许可开源。

### R-09 obsidian-git 未配置

- Vault 没有 `data.json`，即 obsidian-git 从未配置过，autoSave 未启用。
- **影响**：作者手改不会自动提交，需要手动 `git add/commit`，或者干脆不依赖 Git。
- **不擅自配置的原因**：自动提交会把「作者手改」与「CLI 写入」混进同一批提交，
  反而让 `adopt` 的基线判断变模糊。

## 四、结构性风险（设计取舍，不是 bug）

### R-10 备份与原件同机

- `novel backup` 落在同机磁盘，抗不了整机损坏。见 ADR-009。
- **缓解**：作者需自行复制到外部介质；系统不假装做了这件事。

### R-11 本地 Git 不算备份

- 私人 Vault 的 Git 只用于本地 diff 与单文件回滚，历史可被 `reset` 改写。

### R-12 断链检查依赖文件名索引

- `validate` 用文件名（stem）兜底解析双链，同名文件会产生歧义。
- **影响**：可能漏报真实断链，也可能把「指向另一个同名文件」当成已解析。
- **缓解**：`validate` 会同时报告重复 ID，范围是 **Canon 六类 + `04_Story_Assets`**（0.4.1 起）。
  仍不在范围内的目录（`02_Planning`、`05_Ledgers` 等若将来带 `id`）不会被查重——
  「重复 0 份」只等于「这两个范围里没有重号」，不等于全库无重号。

### R-13 隐私扫描只判形状，不判内容

- `scripts/privacy_scan.py` 能认出「私人目录形态」「真实档案命名」「本机路径」「凭据」，
  **认不出**「这段设定写的是我的书」。一段手打的人物小传只要不落在这些形状里，它扫不到。
- **实证一**（较早）：全仓扫过 0 发现之后，人工复核仍在三份文档里发现真实人物名与书名
  （拿来说明「id 与文件名错位」的例子直接用了真名）。已改成虚构的 `示例名` / `林砚`。
- **实证二**（2026-11-20，严重得多）：`maps/jiuzhou.py` 与 `maps/admin.py` 的页面模板嵌了
  **19 项**真实设定（世界名、三层行政示例、规则双链、界外说明、官制表名），
  `known_risks.md` 自己也有 5 项含**情节标题**。扫描器对这三处全部报 0——
  **已经在 `origin/main` 上**（0.4.1 起）。
- **影响**：扫描通过 ≠ 干净。CI 通过只说明「没有命中已知形状」。
- **缓解**：
  1. 形状类规则交给扫描器；内容类只能靠人工过，尤其是有没有用真名、真地名、真书名做示例。
  2. 内容检查的正确做法是**反扫**：从真库索引取实体名、别名、档案标题
     （2026-11-20 实测 902 个），逐个在公仓文本里找。脚本**故意不入库**——它要读的清单
     本身就是私人数据。所以它是**手动重跑**，不是门禁；动过 `maps/`、文档举例、
     测试夹具之后应重跑一次。
  3. 更根本的一条：**别在代码里写作品名**（ADR-005 补充条款）。凡是要写「某个地名」的地方，
     先问「它能不能从 `<project>/00_Project/*.yaml` 读」。写死之后再想清掉，代价是改历史。

## 五、与 PRD v2.1 的已知偏离（T02 引入，均有明确选择理由）

### R-14 编号位数：PRD 六位，实现四位

- PRD §8.1 的表与示例写 `CHAR-000001`（六位）；库内 986 份档案实际是 `CHAR-0001`（四位），
  `task_id` 例外，代码里就是 `TASK-%06d`。
- **选择**：新号一律**四位**，schema 的 pattern 放宽到 `[0-9]{4,6}` 以同时接受两种写法。
- **理由**：改六位要动全库文件名、frontmatter、所有 `[[双链]]`、canvas 节点，收益为零。
- **代价**：schema 不再能拦住「四/六位混用」。混用本身无害（ID 是字符串），
  有害的是「同一个号两种写法」，那由查重负责。

### R-15 通用元数据字段名未迁移

- PRD §8.2 要求 `artifact_type` / `artifact_status`；库内 966 份用的是 `type` / `canon_status`。
  PRD §8.3 还明令禁止再用一个 `canon_status` 混表产物状态／信息性质／审核状态。
- **选择**：`entity` schema 以现状字段（`type`/`canon_status`/`subtype`/`world`）为主，
  PRD 字段名作为可选字段并存，不强制择一。
- **理由**：T02 是「定义契约」，不是「迁移数据」。若按 PRD 严格实现，
  966 份档案会全部非法，`validate` 从「报 1 个重号」变成「报 966 份不合契约」——
  那是把治理问题伪装成验收失败。
- **代价**：两套字段名并存期间，schema 无法阻止有人只写 `canon_status` 不写 `artifact_status`。
  迁移属 T05/T07 的范围，做完才能收紧。

### R-16 两个模型的字段是推断出来的

- `transaction_journal` 与 `execution_receipt`：PRD §8.4 只列了类型名，
  §17.4（22 步执行序列）与 §18.2（崩溃恢复）给了语义，但**没有字段表**。
- **做法**：按 §17.4 的步骤号、§18.2 的「恢复程序基于 active_release / manifest /
  事务日志 / 内容哈希交叉验证」反推字段，并在两份 schema 的 `$comment` 里写明「推断」。
- **影响**：这两份契约可能与作者心里的模型不一致。T06 实现发布内核时应以实际需要为准，
  那时改 schema 是正常的，不算推翻本 ADR。
- 同理 `change_request`：§19.2 只给了中文条目，字段名由本实现命名；
  `revelation_mode` 因 PRD 只示例了 `EXPLICIT`，故意不设枚举。

### R-17 `02_Planning` 里 33 个 ID 形态不合法

- `IdRegistry.compounds` 在真实 Vault 上数出 **33 个**「看着像 ID、形态却不合 PRD」的标识：
  `EVT-CH-0001-001`（7 个事件）、`SCENE-CH-0001-001`（场景卡）、
  `VOL-0001-S1-DETAIL`（卷规划文档）、`LORE-20261104-000000`（导入批次）等。
- **影响**：它们不计入任何前缀的号段。`allocate-id --type EVENT` 会从 `EVT-0001` 起编，
  与既有的 `EVT-CH-0001-001` 不冲突（不同字符串），但**语义上是两套编号并存**。
  命令会提示「另有 N 个复合型 ID 以 EVT- 开头」，不会闷声发号。
- **不改的理由**：改号要动文件名 + frontmatter + 所有引用；而 PRD §8.1 同时禁止
  「仅以章节＋事件序号推导长期稳定 ID」，也就是这两种形态里只有一种能留。
  原计划「迁移属 T03（索引）与 T07（导入）」——**T03 已完成但没做这件事**：
  T03 的六项交付里没有 ID 迁移，本轮只做到「索引里能看见它们」。
  因此改号仍待 T07，或由作者单独裁定。
- **不要把它们当「不是 ID」**：一旦忽略，这些对象在查重时完全隐身。
  `is_compound_id()` 专门收这两类，就是为了让它们可见。

## T03 索引（0.6.0）

### R-18 历史 build 不自动清理

- 每次 `rebuild-index` 写 `index/builds/<build_id>.sqlite`，**不删旧的**。
  **真实 Vault 实测单份 11.5 MiB（12.1 MB）**（1067 产物 / 12867 块）。跑十次就是 115 MiB，
  一天反复调索引很容易堆到几百 MB——本轮调试就留下 5 份、共 62 MiB。
- **选择**：不自动清理。索引是派生物，删错了顶多重跑一次；自动删则要判断「哪份还在被读」，
  而这件事没有可靠答案（读者可能持有打开的文件句柄）。
- **代价**：作者要偶尔看一眼 `index/builds/` 并删掉不要的。`status` 会打「历史 build N 份」，
  算是提醒；但**它不报总占用**，堆到几百 MB 之前不会有人注意。
  彻底清理就是 `rm -rf <runtime>/index` 后重跑。
- **不做 LRU 的理由**：LRU 会在「刚切走的上一个 build」上误删——那正是最可能还要回滚回去的一份。
- **下次要补的**：`status` 报 `builds/` 的总占用，或者加一条 `index prune --keep N`。
  现在只能靠人记得。属 T03 之外的运维缺口，未做。

### R-19 块 ID 与行号绑定「这份文件当时的样子」

- `blocks` 表存 `block_id`（`p0001`…）与 `line_start`/`line_end`。它们是**生成那一刻**的坐标。
  作者手改正文后，同一 `p0001` 可能已经对应别的段落，行号也会整体偏移。
- **影响**：任何跨时间的引用（审阅意见写「p0042 那段有问题」、任务记录挂块 ID）
  在正文改动后就不可信了。**要引用就引「文件 sha256 + 块 ID」**，或者干脆引原文片段。
- **不做块级持久 ID 的理由**：正文是作者用 Obsidian 直接编辑的，没有插入点标记可言；
  想稳定就得往 Markdown 里塞锚点，那会污染正文，违反「正文只给人看」这条。
- 索引本身每次都从 Markdown 重来（ADR-012），所以库内一致性没问题，失效的只是**跨时间的引用**。

### R-20 索引不含 `02_Planning` 以外的语义表

- 17 张表里 **3 张是空表**（`foreshadowing` `dependencies` `issues`）。T04 之后
  `events` / `assertions` / `knowledge` 等六张已会填，但真库只有 `events` 有 **7** 行
  （`05_Ledgers/Events/`），`assertions` / `state_changes` / `knowledge` /
  `revelations` / `event_edges` 都是 **0** 行。
- **风险**：`SELECT * FROM knowledge` 得到 0 行，很容易被读成「这个人确实不知道这件事」，
  而实际是「这张表还没人填」。`state` / `knowledge` 因此一律返回 `NOT_RECORDED`，
  这不是 bug，也不是「世界设定里没有这件事」。
- **缓解**：`index_metadata.populated` / `empty` 分别声明「本版会填」与「建了不填」；
  `rebuild-index` 输出分三行打：会填的表、空表、以及语义表的**实际行数**。
  查询层看到 `NOT_RECORDED` 时必须读成「没记录」，不能读成「没有」（ADR-013）。

### R-21 索引范围包含 `00_System` 与 `90_Shared_Assets`

- 排除的是 `07_Staging` / `08_Reviews` / `90_Archive` / `99_Archive`（后两个是归档），
  但 `00_System`（23 份：策略、提示词、生成看板）与 `90_Shared_Assets`（17 份：模板）
  **仍然进索引**。真实库 1067 份产物里，这两块占 40 份。
- **影响**：`search` 会把 Agent 策略文档、Markdown 模板、Dataview 看板页一起端出来。
  已用结果分层把 `10_Projects/` 排到最前，所以正常查人名地名不会先看到它们；
  但搜「角色」「模板」这类词会命中模板正文。
- **这是待裁的问题，不是结论**。PRD §16.1 的 17 张表都是故事域语义，按这个口径
  `00_System` 本来就不该进；但「全库可搜」也有实用价值（查自己写的策略）。
  **本轮不改**：T03 的六项交付里没有「索引范围」这一项，擅自收窄会把「搜不到」变成新问题。
  作者裁定后再动，届时改 `skip_dirs_from_layout` 一处即可。

## T04 时间线（0.7.0）

### R-22 事件先后要人手写，不写就一律 `UNORDERED`

- `event_edges` 只能从档案里的显式先后关系提取。作者没写「A 在 B 之前」时，
  `EventGraph.compare()` 给出 `UNORDERED`，`state --after X` 会把这类记录留在
  候选池外，最终返回 `UNORDERED` 或 `NOT_RECORDED`。
- **真库当前就是这个状态**：7 个事件、0 条边。每个事件的 frontmatter 有
  `chapter_id` 与 `sequence`，但 `sequence` 的语义（叙述序还是故事序）没有定义，
  **按它连边等于替作者判定倒叙**，所以不连。CLI 在 `UNORDERED` 时会明说
  「事件图有 7 个事件、0 条先后关系」，避免被读成「系统坏了」或「两者同时发生」。
- **这不是缺陷，是唯一诚实的选择**：按 ID 或章节号硬排会替作者编时间线，
  而编出来的顺序会被后续查询当事实继续用，错误会传播（ADR-013）。
- **代价**：想用 `state` / `knowledge` 查得准，就得付出维护事件边的成本。
- **不做「大致按章节序」兜底的理由**：倒叙一章就能让整条时间轴错位，而且错了不报错。

### R-23 认知记录依赖作者显式登记

- `knowledge` 表要的是「谁在什么时候知道/相信什么」，这没法从正文自动推——
  推出来的是猜测，而猜测一旦入库就会以「系统认为」的身份出现。
- **风险**：不登记时 `knowledge` 一律 `NOT_RECORDED`，容易被读成「他不知道」。
- **缓解**：CLI 输出把 `NOT_RECORDED` 解释成「没有记录」，并明确写出「不等于不知道」。

## T05 审批与变更（0.8.0）

### R-24 影响报告是「提及」级判断，不是语义级

- `impact` 用「块文本里出现目标 ID / 实体名 / 别名」来找受影响正文。它是**宁多勿漏**
  的粗筛：名字重名会误报，代词指代（「他」「那人」）会漏报。
- **影响**：`affected_chapters` 可能多列几章，也可能漏掉只靠代词指代的那几章。
  报告是给作者看的清单，不是自动改写的依据。
- **为什么这样也算够用**：RETCON 闸门要的是「作者必须看一眼受影响正文并明确表态」，
  粗筛能保证这一点；精确到段落的语义归属需要 T07 之后的实体识别，本版不做。
- **缓解**：`notes` 里会说明目标有没有实体档案（没有时只剩 ID 匹配，可能偏少），
  mention 里记下命中的词与类型（`name` / `alias` / `id`），便于人工核对误命中。

### R-25 批准按「改一个字节就失效」，没有非实质修改白名单

- PRD §14.5 要求批准绑定内容指纹。本版不做「这是不是实质修改」的判断：
  改一个标点也要重新批准。
- **代价**：作者手改一个错字后要重走 `inspect → approve`。
- **不做白名单的理由**：MVP 没有可靠的「实质」判据，判错的代价是发出去的东西
  没人真看过。白名单留到 P1，届时也必须由作者显式开启。

### R-26 「最近一次批准」按记录顺序取，不按时间戳排序

- `ApprovalStore.latest_for()` / `for_target()` 取的是按文件名排序后的最后一条。
  文件名是 `APR-00000N` 递增，正常情况下等价于「最新」。
- **风险**：手工复制旧批准文件、或从备份恢复单个文件，会让编号与时间顺序不一致，
  此时「最近一次」可能取到较旧的那笔。
- **当前不修的理由**：修法是按 `approved_at` 排序并处理同一秒的并列，属健壮性改进，
  不在 T05 验收范围内。**已知且记录在案**，恢复备份后建议整目录一起恢复。
